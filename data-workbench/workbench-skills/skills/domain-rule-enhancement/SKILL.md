## What this skill does

Reads structured domain rule reference files (YAML) and optional free-form guidance (markdown) to generate domain-aware data quality rules. These rules represent what the data **should** look like based on domain knowledge, as opposed to the observation-based rules generated by data-quality-rule-generation which describe what the data **does** look like.

All generated rules are tagged with `ruleSource: 'domain'` and `status: 'pending_review'` so they must be reviewed and approved before they affect scoring.

## IMPORTANT: No LLM Judgment for Rule Invention

**Your role is to MATCH and APPLY rules from the reference files and guidance, NOT to invent new rules.**

- Apply all matching rules from the structured YAML reference files mechanically
- Interpret the free-form guidance file to identify additional rules described there
- Do NOT generate rules that are not documented in either the reference files or the guidance file
- If a column does not match any pattern in the reference files or guidance, do NOT create a rule for it

This ensures reproducibility — the same data should produce the same domain rules every time.

## Workflow

### Step 1: Generate domain rules Cypher

```bash
python {skill_dir}/scripts/generate_domain_rules.py \
  --host {neo4j_host} --bolt-port {neo4j_port} \
  --username {neo4j_user} --password {neo4j_password} \
  --database {neo4j_database} \
  --domain "{domain}" \
  --project-code {project_code} \
  --reference-dir {skill_dir}/reference
```

**Note:** `--project-code` is **REQUIRED** when provided in the prompt to scope queries and URIs to this project.

This script:
1. Loads `common.yaml` + `{domain}.yaml` from the reference directory
2. Loads `guidance/{domain}.md` if it exists
3. Queries Neo4j for all columns with their approved descriptions and data types
4. Matches each column against the structured YAML rules
5. For guidance-based rules, YOU (the agent) read the guidance file and tell the script which additional column-rule pairs to generate via `--extra-rules` JSON
6. Generates `cypher_scripts/domain_rules.cypher`

### Step 2: Review guidance file for additional rules

If a guidance file exists at `{skill_dir}/reference/guidance/{domain}.md`, read it and identify any rules it describes that were not covered by the YAML patterns.

For each additional rule, call the script with `--extra-rules`:

```bash
python {skill_dir}/scripts/generate_domain_rules.py \
  --host {neo4j_host} --bolt-port {neo4j_port} \
  --username {neo4j_user} --password {neo4j_password} \
  --database {neo4j_database} \
  --domain "{domain}" \
  --reference-dir {skill_dir}/reference \
  --extra-rules '[{"col_uri": "column:schema.table.col", "rule_type": "range", "min": 0, "max": 100, "severity": "sh:Warning", "rationale": "From guidance: ..."}]' \
  --append
```

### Step 3: Load domain rules to Neo4j

```bash
python {skill_dir}/scripts/run_domain_rules.py \
  --host {neo4j_host} --bolt-port {neo4j_port} \
  --username {neo4j_user} --password {neo4j_password} \
  --database {neo4j_database}
```

### Step 4: Report results

Summarize what was generated:
- How many rules from structured reference files
- How many rules from guidance
- Which columns were matched
- Which columns had no matching patterns (for transparency)

## Reference File Format

### Structured rules (YAML)

Located in `reference/common.yaml` and `reference/{domain}.yaml`.

```yaml
domain: human_resources
rules:
  - match:
      description_contains: ["birth", "born", "dob"]
      data_type: ["date", "timestamp"]
    rule:
      type: range
      min: "1900-01-01"
      max: "today"
      severity: "sh:Warning"
      rationale: "Birth dates should be within a reasonable human lifespan"
```

Match criteria (all must match if specified):
- `description_contains` — list of keywords; at least one must appear in the column description (case-insensitive)
- `data_type` — list of SQL data types; column's data type must match one (prefix match, e.g., "timestamp" matches "timestamp with time zone")
- `name_contains` — list of keywords; at least one must appear in the column name (case-insensitive)

Rule types:
- `range` — min/max bounds. Use `"today"` as a special value for current date.
- `allowedValues` — explicit list of allowed values, or `values_file` pointing to a text file (one value per line)
- `pattern` — regex pattern the value should match

### Guidance (markdown)

Located in `reference/guidance/{domain}.md`. Free-form text describing additional domain rules that don't fit the YAML pattern format. Example:

```markdown
## HR Domain Guidance

- In the payroll schema, salary columns should never be negative
- Employee grade is a numeric field from 1-15, not a letter grade
- The company was founded in 1985, so no employment dates should precede that year
```

## Graph Model

### Nodes created

`:PropertyShape` with additional properties:
- `ruleSource: 'domain'` — distinguishes from observation-based rules
- `status: 'pending_review'` — requires human approval before affecting scoring
- `domainRuleRef: '{domain}.yaml#rule-N'` — traces back to the reference file entry
- Standard PropertyShape properties: `uri`, `ruleType`, `path`, `severity`, `confidence`, `description`

### Relationships

Same as standard DQ rules:
- `(:NodeShape)-[:PROPERTY]->(:PropertyShape)` — links to the table's shape
- `(:PropertyShape)-[:ON_COLUMN]->(:Column)` — links to the target column
