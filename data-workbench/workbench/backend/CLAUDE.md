# Backend CLAUDE.md

Backend-specific detail for `workbench/backend/`. The root `CLAUDE.md` at the repo root covers orientation, SA/CF distinction, graph isolation, and architecture overview — read that first.

## Workflow groups by archetype

- `dpe-sa` default: `data_discovery` → `metadata_enrichment` → `source_naming_recommendations` (column-name standardization) → `mark_discovery_complete` → `po_source_validation` → `product_materialization_sa` (synthesize ODCS from graph → odcs_to_dprod → auto_mapping_sa → serving_virtual_view → deploy_virtual_view → deployment_reflection → mark_engineering_complete). `serving_virtual_view` and `serving_physical_copy` are the exclusive serving group (deploy/reflection are optional). DQ workflows (`baseline_dq_rules`, `dq_testing`, `dq_scoring`) intentionally **omitted** from defaults — engineer adds them via the catalog if quality assessment is wanted.
- `dpe-cf` default (post-split, lean): `product_definition` (initiate + odcs_specification) → `odcs_to_dprod` → `integration` (data_mapping → serving_virtual_view → deploy_virtual_view → deployment_reflection → mark_engineering_complete). Consumer products inherit discovery/profiling/enrichment/DQ context from CONSUMES'd source products; those workflows are addable but no longer default.
- `dq` / `dd`: discovery + DQ stack as before.

## SQLModel models (`models.py`)

Core tables: `Project` (`archetype`, `domain`, `product_idea` (free-form PO prose for SA), `owner_email`, `owner_name`, `discovery_complete_at`, `workflow_json`, `multi_workflow`), `Workflow`, `AppSettings`, `StageRun`, `StageExecution` (one row per stage run with `log_json` capped at 2MB), `DQTestRun`, `ProductRequest`, `IngestDraft` (in-flight consumer-aligned ODCS ingest), `MarketplaceGap` (consumer-logged gaps against a product), `MaterializationTarget` (per-product dbt target DSN), `ChatSession`/`ChatMessage`, `ProductChatSession`/`ProductChatMessage`. `StageStatus` enum: `pending | running | awaiting_review | complete | failed`. `ProductRequestKind`: `new | edit | ingest | source-rediscovery | consumer-pushback | source-candidates-needed`. `ProductRequest` carries optional `parent_ingest_draft_id` (cross-link to the ingest draft that spawned a source product) + `gap_column_uri` / `gap_reason` (engineer→PO escalation context). `_migrate()` in `database.py` runs `ALTER TABLE` in try/except for column adds.

## Stage registry and pipeline (`archetypes.py`, `pipeline.py`)

`STAGE_REGISTRY`: stages keyed by string ID, each with `skill`, `owner_role`, `requires_llm`, `has_review`, `review_type`, `config_fields`, `prompt_template`. Composite stages chain sub-stages via `sub_stages`.

`build_prompt()` substitutes `{project_code}`, connection details, stage_config, playbook instructions. Prepends a skill-loading directive when a stage has a `skill`; appends an anti-exploration system prompt. **Archetype-aware injection**: when stage_id is `data_mapping` and `project.archetype == 'dpe-cf'`, fills `{source_mode_directive}` instructing the agent to use `--source-mode dprod --target-contract <id>` (consumer-aligned mappings target `:DProdColumn` from CONSUMES'd source products, not raw catalog).

**Non-LLM backend-driven stages.** DQ test gen/exec stages bypass the SDK, spawn skill scripts as subprocesses with 5/30 min ceilings, and write `:TestRun`/`:TestResult` to Neo4j on success. Other non-LLM stages (`initiate`, `odcs_specification`, `odcs_to_dprod`, `publish`, `mark_discovery_complete`, `synthesize_odcs_from_graph`, `auto_mapping_sa`, `mark_engineering_complete`) complete via `POST /stages/{n}/complete`. The frontend's `Pipeline.tsx:NON_LLM_ACTIONS` map wires each to its specific button label + post-action; **omitting an entry means clicking Run hangs forever** because the stage has no skill or prompt. A few non-LLM stages complete through their OWN endpoints, not `/complete`: `select_data_source` (via `set_data_source`), `deploy_virtual_view` (`routers/serving.py` deploy), `deploy_physical_copy` (`/serving/materialize` via the MaterializationGateDialog), `deployment_reflection` (`/reflection/run`); `po_source_validation` is a PO review gate (no Run at all). The serving **Build** stages (`serving_physical_copy` → `/serving/dbt/build-package`, `serving_lakehouse_export` → `/serving/lakehouse/build`) build the package with no live DB, then post `/complete` (see the uniform Configure → Build → Deploy split under "Serving mode").

**Re-run of a non-LLM stage routes through its OWN action, NOT the WS `run_stage` path.** `Pipeline.tsx:handleRerunConfirm` dispatches a completed non-LLM stage's Re-run through its `NON_LLM_ACTIONS` entry — identical to first-run. Sending it through `onRunStage`/WS instead strands the card at "Complete · Running…" forever: `start_stage_run` returns early for non-LLM stages and does no work, so `runningStage` never clears (defense-in-depth: that early return now also emits a terminal `stage_status_changed` so a WS caller unsticks anyway). Two groups, split by `NON_LLM_CONFIG_STAGES`:
- **Self-completing actions** (build/deploy/publish/`odcs_to_dprod`/`mark_engineering_complete`/`dmig_*`/`cmig_*`, which call `/complete` internally) are **reset to `pending` first** — else the coupled `/complete` 400s on an already-`complete` stage.
- **Config/edit dialog stages** (`NON_LLM_CONFIG_STAGES` = `odcs_specification`, `select_data_source`, `configure_serving`, `configure_dq`, `configure_transfer_placement`) run **WITHOUT a reset** — their dialogs guard `/complete` on `status ∈ {pending, running}` (or complete via a dedicated endpoint), and not resetting avoids stranding the stage at `pending` when the engineer cancels the dialog. `dmig_configure` is deliberately NOT in this set (its `ConfigureMigrationDialog` calls `/complete` *unconditionally*, so it needs the reset-first default).

**Stage lifecycle resilience.** Background SDK tasks survive WS disconnects (`_active_tasks`). `_resolve_orphaned_stages` in `routers/stages.py` fires on `GET /stages` and marks stages stuck in `running` longer than `ORPHAN_TIMEOUT_SECONDS` (5 min) as `complete` / `awaiting_review` based on Neo4j state.

**SDK integration** (`sdk_runner.py`): monkey-patches the SDK's `parse_message` for unknown types; system prompt always carries the anti-exploration directive; agent-to-user messaging via `scripts/agent_ask.py` parks the request and relays through WebSocket. WS protocol at `routers/websocket.py`: client sends `{action: "run_stage", stage_number, workflow_id, stage_config}`.

## Review system (`routers/reviews.py`)

Review surfaces: `descriptions`, `mappings`, `domain_rules`, `transformation_escalations` (Steward), `unmapped_columns` (engineer manual mapping), `source_product_validation` (PO combined gate for SA — names + descriptions + observation rules in three tabs). Each has GET (list pending) + POST (approve/reject/edit) carrying W3C PROV-O provenance.

**Per-stage scoping** (`components/ReviewPanel.tsx`): the Reviews tab is scoped to the active stage's `review_type`. `RELEVANT_REVIEW_TYPES`: `descriptions → [descriptions]`, `mappings → [mappings, unmapped_columns, transformation_escalations]`, `domain_rules → [domain_rules]`, `source_product_validation → [source_product_validation]`. The mapping stage owns the cross-cutting unmapped/escalation surfaces.

**dpe-sa: PO owns description approvals.** ReviewPanel takes an `archetype` prop; for `dpe-sa` it suppresses the engineer-side `descriptions` panel — the PO approves descriptions in `SourceProductValidationPanel` (mounted on `po_source_validation` stage and at `/product/validate/:projectId`). The engineer's `metadata_enrichment` stage still flips `awaiting_review → complete` automatically when the PO clears the queue (see below).

**Auto-flip semantics.** `_check_review_complete` walks ALL stages whose `review_type` matches the just-approved type and looks for `pending` / `awaiting_review` / `failed` status; flips them to `complete` when remaining count = 0. `pending` is included so PO-only gates (`po_source_validation`) — which never get a Run click — still close. The `GET /reviews/source_product_validation` handler also calls `_check_review_complete` so opening an already-empty panel resolves stale state.

**Mapping queries are dual-source.** `:ColumnMapping`'s source is either `:Column` (catalog) or `:DProdColumn` (consumer-aligned). All mapping-related queries (`PENDING_MAPPINGS_QUERY`, `GRAPH_MAPPINGS_QUERY`, `MARKETPLACE_MAPPING_GRAPH_QUERY`, `MAPPINGS_DETAIL`, `MAPPING_STATS`, `SOURCE_COLUMNS_QUERY`, summary lineage) use the dual-OPTIONAL pattern with `coalesce(...)` in RETURN. Two load-bearing Cypher gotchas to know before touching these:
- **WHERE-positioning**: a trailing WHERE after a chain of OPTIONAL MATCHes binds to the LAST OPTIONAL pattern (Cypher grammar), turning it into a per-pattern guard rather than a row filter — push the row filter into a `WITH` separator before the OPTIONAL chain.
- **Variable-name reuse**: when the dual pattern references `:DProdOutputDataset` on both the consumer side and the source side, rename the source-side binding (e.g. `src_ods`) — Cypher treats repeated bindings as equality constraints, which silently forces source ods == consumer ods and zeros the dprod match (the bug that misclassified every dprod-sourced mapping as `literal` in `generate_view_ddl.py:MAPPINGS_QUERY` before the fix).

These queries traverse the **primary** `:MAPS_SOURCE_COLUMN` edge only. A `lookup` transform's reference table is surfaced separately via `:LOOKUP_VIA` (see Transformations § below) — the marketplace + engineer graph handlers run a companion `*_LOOKUP_GRAPH_QUERY` and fold the rows in with `lookup_via.merge_lookup_graph_rows`. Don't try to bolt lookup sources onto the dual-OPTIONAL chain.

**Approve / Replace / Escalate on `MappingReviewPanel`.** Three first-class actions on an AI-suggested mapping:
- **Approve** with a quality rating (Acceptable / Good / Excellent) signs off as-is. **Escalate** sends the mapping to the Data Steward.
- **Replace** is the single unified override — covers transform-fragment edits, source-set edits, and remap-to-different-source-column in one Save Replacement POST. Requires a rejection category (defaults to `edited_default`) and writes a `:ProvRejectionReason` linked to the activity — changing the AI's default ALWAYS records *why*. View mode is read-only; the engineer must click Replace to mutate anything. Backend `replace_mapping` branches on `remap_source_uri`: present → `REJECT_MAPPING_QUERY` + `REMAP_MAPPING_QUERY`; absent → `REPLACE_TRANSFORM_QUERY`. Source-set reconciliation reuses `WIPE_MAPPING_SOURCE_EDGES` + `ATTACH_MAPPING_SOURCE_EDGE_{COLUMN,DPRODCOLUMN}` (label dispatched by URI prefix). Legacy `edit_transform` / `reject` actions remain in the handler for back-compat but the frontend no longer emits them.
- **Original AI suggestion disclosure.** Pending-mapping rows include `original_ai_suggestion` — populated by a `CALL` subquery pulling the earliest `:ProvActivity {activityType: 'transformation_authoring', priorAuthor: 'ai_suggestion'}`. When present alongside `transform_author === 'engineer'`, MappingReviewPanel renders a collapsible "Original AI suggestion (replaced)" panel.
- `SOURCE_COLUMNS_QUERY` returns both `:Column` and `:DProdColumn` so the picker works for both archetypes (UnmappedColumnsPanel + MappingReviewPanel share the endpoint and `SourceColumn` type). It also surfaces `table_schema` / `table_name` / `column_name` for `TransformEditor`'s lookup-arm `<datalist>` autocompletes; the freeform input remains so engineers can type undiscovered reference tables.
- **Re-run from the panel.** **Refresh** (POST `/stages/{n}/reset` then WS `run_stage` — keeps existing rows) and **Start over** (POST `/reviews/mappings/wipe` first — soft-deletes every project-scoped `:ColumnMapping` with `status='superseded'`, `isCurrent=false`; then reset+run). `superseded` is a new status value; downstream filters key on `status='approved'` or `isCurrent=true`, so superseded rows disappear without code changes. Audit chain is preserved because the wipe is soft. `handleRerunStage` in `ProjectDetailPage.tsx` is shared with Pipeline.tsx's Rerun button.

## Source-aligned (`dpe-sa`) flow specifics

**Wizard.** `NewSourceProductWizard.tsx` — 3-step lightweight: idea (free-form prose) + domain + name. POSTs `/api/projects` with `archetype='dpe-sa'` + `product_idea`; then `POST /product-requests/submit` (kind `new`). No ODCS spec at submit — synthesized later.

**Engineer pipeline.** Engineer reads `Project.product_idea` from a banner (`ProductOwnerContextBanner`) on the project page. Pipeline runs discovery → enrichment → naming → mark_discovery_complete (which stamps `Project.discovery_complete_at`). PO sees the request flip to "Ready for your validation" on `MyProductsDashboard`'s in-flight section (`/api/my-products/in-flight`).

**Accept-gate prerequisite.** The PO source-validation gate (`po_source_validation`) stays **locked until the engineer accepts the request** (`ProductRequest.status` `submitted → accepted`, via `accept_request` MCP tool / `POST /product-requests/{id}/accept`). This is otherwise silent, so two surfaces flag it: `ProjectAcceptBanner` on the engineer project page (inline Accept), and `get_plan_summary` — for `dpe-sa` with a `submitted` request it overrides `recommended_next` to the `accept_request` action and adds it to `blocked` rather than recommending the locked stage.

**PO validation gate.** `SourceProductValidationPanel` has five tabs (Names / Descriptions / **Tables** / **Relationships** / Rules). All actions emit PROV-O activities + agents. Name reject writes `:ProvRejectionReason {category, detail}`; approve carries `quality`. The Tables tab surfaces per-`:Dataset` `:TableDescription` items with the `relationshipKind` classification — PO approves text + kind. The classification drives the consumer-side view-DDL bridge ranker (`general_membership` outranks `specialization`). Descriptions and observation-rule reviews are PO-owned for SA — engineer Reviews tab hides descriptions on `dpe-sa` archetype.

**Table descriptions** (`:TableDescription`). Sibling of `:ColumnDescription`, generated by `metadata-enrichment` skill's `write_table_descriptions.py`. Attached to `:Dataset` via `:HAS_TABLE_DESCRIPTION` (distinct from column descriptions' `:HAS_DESCRIPTION` rel — keeps queries unambiguous). Carries `text` + `relationshipKind` ∈ {`fact`, `lookup_dimension`, `general_membership`, `specialization`, `audit_log`, `configuration`, `unknown`} + standard `status` / `isCurrent`. Approved descriptions propagate to `:DProdOutputDataset.description` / `:DProdOutputDataset.relationshipKind` during `_generate_dprod` (`DPROD_PROPAGATE_TABLE_DESCRIPTION`). Shared chip `components/RelationshipKindChip.tsx` renders the classification in five surfaces: marketplace detail, engineer `datasets` dashboard card, source-pickers in MappingReviewPanel + UnmappedColumnsPanel, PO Tables tab. Backend extensions live in `marketplace.py:PRODUCT_DETAIL`, `summary.py:DATASETS_DETAIL{,_S}`, and `reviews.py:SOURCE_COLUMNS_QUERY{,_S}`.

**Materialization.** `synthesize_odcs_from_graph` (in `sa_pipeline.py`) walks approved `:Column.recommendedName` (or original col.name when status='rejected'/unset), `:ColumnDescription`, `:PropertyShape` (observation, approved); builds an ODCS dict with `primaryKey`/`required` propagated from `:Column`; writes via `_save_odcs_to_graph`. `auto_mapping_sa` writes 1:1 `:ColumnMapping` rows from each `:Column` to its corresponding `:DProdColumn` (no LLM mapping pass — PO already approved names). The synthesized table description is composed from schema/table + profiled `row_count` (lightweight; future skill work can replace with LLM-generated prose).

**FK propagation onto `:DProdOutputDataset`.** `_generate_dprod` (`odcs.py`) runs `DPROD_PROPAGATE_FK` to mirror catalog `:Dataset—[:REFERENCES]→:Dataset` edges as `:DProdOutputDataset—[:REFERENCES]→:DProdOutputDataset` (matched by `physicalName == :Dataset.name`, same `columns` / `referencedColumns` payload). Without this, a downstream consumer-aligned product CONSUMING this source can't FK-discover joins across the source's per-dataset views, and `data_serving_virtual_view` either emits a wrong single-table SELECT or raises `ViewGenerationError`. `DPROD_WIPE` cascades through ods nodes so propagated edges clear every rebuild. No-op for consumer-aligned source products whose schemas don't mirror catalog datasets. Consumer side: `generate_view_ddl.py:DPROD_FK_QUERY` reads these edges; `_resolve_source_relation` keys dprod sources on `source_dprod_dataset_physical` (one view per source dataset).

**Pipeline UI for SA.** Engineer's pipeline hides PO-only stages (`po_source_validation`) via `PO_STAGE_IDS`. `Pipeline.tsx` derives a `blocked_on_po` display state for the head materialization stage (`synthesize_odcs_from_graph`) when the PO gate isn't complete — renders amber **"Pending PO validation"** with Run disabled.

## Consumer-aligned (`dpe-cf`) flow specifics

**Wizard.** `NewProductWizard.tsx` — 10 steps (contract-first ordering; `STEP_LABELS` in the wizard is the source of truth):
1. Describe & Choose Domain
2. Shape (dataset-level: grain prose, filter predicate, SCD policy — Phase 2/3/4/5 of `:DatasetTransform` authoring)
3. **Suggest candidate sources (optional)** — mid-wizard pre-selection of source-aligned data products. Auto-fires `/api/ingest-products/match-inputs` against the wizard's partial spec; picks here feed `source_contract_ids` into the schema advisor at step 4 for feasibility-aware column ranking. **Skippable** — `canAdvance=true` regardless of selections.
4. Shape the Schema (column-level authoring + per-column "Group by" → `:DatasetTransform.grouping_keys`)
5. Product Details (name / description / purpose / dataset name)
6. **Operations & Support** (SLA / contacts / roles — all optional; inherited from sources where available)
7. Rule Coach (domain rules — `/odcs/suggest-domain-rules`)
8. Readiness Review (optional pre-flight: OSI Readiness Score + Question Analysis, both manual-fire, aligned empty-state)
9. **Confirm candidate sources** — required submit gate. Pre-populated from step 3 picks; PO can add/remove; includes a **Pre-flight gap check** section (manual-fire button; LLM-summarised or heuristic per-column status). Submit blocked on `wizardSlots.length > 0 && allSlotsMatched(wizardSlots)`; soft-confirm dialog when gap-check found unresolved gaps.
10. Submitted

Submit emits ODCS with `inputs[]` from matched slots; backend MERGEs `:CONSUMES` edges. **Edit-mode hydrates `selectedSourceInputs` from `spec.inputs`** AND `shapeGrain` / `shapeFilter` / `shapeScdPolicy` / `groupingKeys` from `spec.schema[0].transform` so removing/adding inputs and shape choices round-trip through versioned-contract branching. Both step 3 and step 9 mount the shared `<ResolveAndBindSourcesStep>` (in `pages/product/shared/`); state syncs through a single `wizardSlots` + `selectedSourceInputs` pair. The wizard also accepts `?step=N&from_request=ID` query params for engineer-initiated edit-mode entry (see "PO ↔ Engineer feedback loops").

**ODCS canonicalisation** (`odcs.py:_canonicalize_v3_1`): `inputs` is a known top-level key; entries normalised to `{dprod_uri, contract_id, name}` (camelCase aliases accepted, empty `dprod_uri` filtered, empty list drops the key entirely).

**`:CONSUMES` in `_save_odcs_to_graph` (multi-hop, DAG-guarded, atomic).** A consumer (`dpe-cf`) may `:CONSUMES` ANY published product — source / aggregate / consumer — forming multi-hop DAG chains (A→B→C). The sync (`sync_consumes_edges`) is **diff-aware soft-expire** (NOT wipe-and-rebuild): active edges not in the incoming set get `toVersion` set; re-added edges are reactivated via `MERGE_CONSUMES_EDGE`'s `ON MATCH`/`FOREACH` reactivation arm (clears `toVersion`, rebases `fromVersion`), so a removed-then-readded input isn't left dead. `MATCH` (not MERGE) on the target `:DProdDataProduct` — typoed inputs drop the edge rather than spawn phantoms.
- **Atomic + DAG-guarded.** `save_contract_head` + `save_contract_substructure` + `sync_consumes_edges` run in ONE explicit Neo4j write tx. Before any mutation, `validate_consumes_bindings` (Phase 0 keystone) validates the COMPLETE incoming edge set: rejects self-consumption, any binding whose target can already reach the consumer (`would_create_cycle` — a pure BFS over the alternating `DataContract-[:CONSUMES]->DProdDataProduct<-[:MATERIALISES_AS]-DataContract` shape, over the union of head + latest-deployed active edges), an unknown target, a target with no published/superseded version, or an unsupported `productKind`. A rejection raises `ConsumesBindingError` → 409, leaving the contract head + edges byte-unchanged. A per-graph sentinel write-lock (`acquire_topology_lock`) serialises reciprocal writes across workers. Rollout audit: `scripts/audit_consumes_cycles.py`.
- **Active-edge convention.** All operational `:CONSUMES` reads filter to the active set — `WHERE r.toVersion IS NULL` (currently-active) or the `fromVersion<=$v<=toVersion` window: `qa.READ_CONSUMES`, `stages.UNMAPPED_CONSUMED_DATASETS`, SLA inheritance `SUGGEST_SLA_FROM_SOURCES`, and `pg_resolver`'s borrow/serving queries. (`filter_intent._GROUNDING_QUERY` reaches sources via `:ColumnMapping`, not `:CONSUMES` — no filter needed.)

**Mapping.** Engineer's `data_mapping` stage gets the archetype-aware directive (see `pipeline.py:build_prompt`). The skill (`workbench-skills/skills/data-mapping-neo4j/`) takes `--source-mode {catalog,dprod}` and `--target-contract`. dprod mode walks `(dc:DataContract)-[:CONSUMES]->(:DProdDataProduct)-...->(:DProdColumn)`. `write_mappings.py` auto-detects source URI prefix (`column:` → `:Column`, `dprod:col:` → `:DProdColumn`). `generate_view_ddl.py` resolves source schema/table per row: catalog → raw schema/table; dprod → `(view_schema, vw_<safe_name(source_dprod_dataset_physical)>)` — one view per source product's `:DProdOutputDataset` (single-Postgres-instance assumption for v1).

**Recovery: consumer serving fails with no-FK-path.** When `data_serving_virtual_view` raises `ViewGenerationError: source table X is referenced by mappings but no FK path connects it to other tables`, first try re-running `odcs_to_dprod` on the **source** project — `_generate_dprod` is idempotent and `DPROD_PROPAGATE_FK` mirrors catalog FK edges onto the source's `:DProdOutputDataset` chain. Source products materialised before that propagation shipped lack those edges and need a one-time re-run. The error message itself enumerates the four causes (stale propagation, missing bridge in mappings, undiscovered catalog FK, junction table in a not-CONSUMES'd product). **Catch it up front:** `GET /api/projects/{id}/serving/join-preflight` (`backend/join_preflight.py`) detects when a dataset's mapped base tables split into disconnected components — the common cause is a consumer mixing tables from **two source products** (`:REFERENCES` never crosses products) — and returns a `recommended_joins` payload (a `:DatasetTransform.joins[]` bridge) shaped for one-click apply via `PUT /dataset-transform/joins`. Auto-bridging **chains transitively over shared identity keys** (account→transaction→customer) and can pull in a **junction dataset from a CONSUMES'd product** as a pure bridge (`bridge_only`, emitted as a `SELECT DISTINCT` of the link keys so ledger grain can't fan out); a tie among junction candidates is surfaced as `junction_candidates`, never guessed. The `data-mapping-neo4j` skill (Step 3.6) runs the same check while authoring so it recommends the bridge instead of emitting a dead-end mapping. When materialization hits this, `routers/materialization.py` now surfaces it as a clean **422** (with the actionable message), not an opaque 500.

**FK-driven join construction.** `_build_from_fk_inferred` walks `:REFERENCES` between mapped tables and BFS-discovers bridge tables when mapped tables aren't in one direct-FK connected component. Bridges contribute no SELECT columns. Multiple shortest paths get ranked by name-similarity + PO-approved `:TableDescription.relationshipKind` (`general_membership` > `specialization`); tied top tier raises `_AmbiguousBridges`. History-shaped bridges matching `_TEMPORAL_PATTERNS` are auto-wrapped with `ROW_NUMBER()`. **Mapped SCD satellites** (non-bridge LEFT-joined tables with an `is_current` flag or effective-dating `from/to` pair — `_satellite_needs_dedup`, which overrides a coarse `audit_log` label) are ALSO current-row-wrapped so a lookup keyed off them (e.g. `job_title` via `job_assignment_history.job_id`) can't fan out; reported in `summary['auto_satellite_dedup']`. The **explicit-join path** (`_build_from_explicit`, when `:DatasetTransform.joins[]` is set) applies the same wrap — so a consumer can anchor on one source product's table and bridge to another product's history table without fan-out. Remaining temporal-but-not-strongly-SCD tables still emit `summary['multiplication_warnings']`; band/grade/tier-named columns with no bucketing emit `summary['semantic_warnings']` (raw-value leak). Full algorithm, ranker weights, override paths in **`docs/architecture/view-ddl-fk-bridges.md`**.

**Lean default template.** `dpe-cf` default is `product_definition` → `odcs_to_dprod` → `integration` — discovery/profiling/enrichment/DQ are addable from the catalog, not scaffolded. Backend dispatch (`pipeline.py`, `stages.py:config-options`) is archetype-based, not Neo4j-probe-based.

## Blueprint Library — data-product spec templates (`routers/templates.py` + `template_store.py` + `template_corpus.py` + `feasibility_map.py`)

The **single source of truth for data-product spec templates** (UI: "Spec Templates", `/product/templates`; router prefix `/api/templates`). Consolidates three legacy stores: A (`playbook/odcs_templates/*.yaml`), B (`playbook/discovery/reference_data_products.yaml`), C (the feasibility corpus). Every workflow-facing consumer reads **only `templateStatus='published'`** templates.

- **Storage:** `:DataContract:ProductTemplate` nodes on the **global AppSettings graph** (`estate.estate_graph_session`), id `template:{slug(domain)}:{slug(spec_id)}`, **never** linked to a `:Project`, `_generate_dprod` **never** run on them. The dual label + `template:` id prefix keep templates out of every broad `:DataContract` / marketplace / lineage / feasibility traversal by construction (those require a `:MATERIALISES_AS`→`:DProdDataProduct` edge or a `(:Project)-[:HAS_...]->` link a template lacks). Head props: `isTemplate`, `templateStatus` (draft|published), `templateOrigin` (seed|clone|import|authored), `templateOwnerEmail`, `templateDomain`, `sourceSpecId`, `clonedFrom` (+ a `:PROV_WAS_DERIVED_FROM` edge for clones).

## Connected Estate + top-down feasibility (`estate*.py` + `feasibility*.py`)

A **top-down** Product-Workbench entry point (user guide: **`docs/connected-estate.md`**), and a **SEPARATE bounded context** from the Pulse-backed estate discovery (`routers/discovery.py` + `playbook/discovery/estate.yaml`, which presents a Pulse *assessment* bottom-up). Here DW connects to a live platform itself, scans the estate, and grades a catalog of desired **reference data-product specs** with a stoplight (`ready` | `adaptable` | `assemblable` | `absent`). The Pulse routes/files/UI/MCP are **untouched** — a future Pulse convergence is an adapter INTO this model, never a prerequisite (boundary pinned by `tests/test_connected_estate_boundary.py`).

- **SQL models** (`models.py`): `Estate` (business scope) / `EstateSource` (a `PlatformConnection` + namespace policy) / `EstateScan` (one leased, versioned snapshot) / `EstateScanNamespace` (per-namespace selection+outcome) / `FeasibilityRun` (leased, version-stamped) / `FeasibilityScore` (per-spec verdict) / `FeasibilityCandidate` (PO-flagged score saved as a pipeline idea, de-duped on `(score_id, saved_by)`, `status ∈ {saved,dismissed}`). Split deliberately — a rescan is a new `EstateScan` row (monotone `scan_version`), not a mutation of identity. New tables → `create_all`; the later `EstateSource.catalog` + `FeasibilityRun.scan_ids_json` columns are added by `_migrate()` ALTER.
- **First-class graph identity** (`estate.py`): `(:Estate {uri:"estate:{id}"})-[:HAS_SCAN]->(:EstateScan {uri, version})-[:OBSERVED]->(:EstateDataset {uri:"estatedataset:{estate}:{source}:{db}.{schema}.{table}"})-[:HAS_COLUMN]->(:EstateColumn)`. Collision-safe (source+db+schema+relation). Written **directly from Python** on the global AppSettings graph (the Pulse discovery loader is NEVER touched). **Rescan diff**: new added / changed schemas versioned (`schemaHash`) / deleted tombstoned (`deletedInScan`) / profiles stale-marked; feasibility reads pin to one scan via `:OBSERVED`.
- **Graph-native column embeddings (feasibility reuse).** Text-similarity vectors are computed ONCE at **enrichment** time and stored on `:EstateColumn` (`embedding` + `embeddingTextHash` + `embeddingModel` + `embeddedAt`), NOT recomputed per feasibility run. `estate_enrich._enrich_schema` writes them after column descriptions land, **off the event loop** (`asyncio.to_thread(estate.embed_and_store_columns, …)` — fastembed encode is CPU-bound; see the freeze in `research/2026-08-24-background-jobs-and-async-freeze.md`). **Content-hash keyed** (`embeddingTextHash = sha256(text)` + `embeddingModel`): an unchanged re-enrich is a no-op; a rescan/description-edit/model-swap re-keys → recompute. The **canonical embed text** is `schema_dna.estate_column_embed_text(name, description)` → `"{name}. {description}"` (name only when no description) — it MUST equal `ColumnFeature(name=…, concept="", description=…).semantic_text()`, which is exactly how `feasibility._raw_evidence` composes the estate `ColumnFeature` (that alignment dropped the old `desc or name` duplicated-name text — a minor, deliberate scoring tweak). A native vector index `estate_column_embedding` (`ensure_estate_vector_index`, mirrors `business_concepts.ensure_constraints`; created at enrich start) over the 384-dim cosine vectors enables reuse now + future "find similar estate columns" search. Feasibility READS the vectors — `estate.read_estate_datasets`'s per-column projection carries `embedding` (kept OFF `read_scan_datasets`, which feeds the frontend/FK scan), and `_raw_evidence` seeds `schema_dna.score_matrix(embed_cache=…)` with `{semantic_text(): vector}` so the estate (target) side isn't re-embedded during a run — only the small spec-attribute set is. Backfill (pre-embedding scans / model swap): `estate.backfill_estate_embeddings(settings, scan_id)` + `scripts/backfill_estate_embeddings.py`. Degrades gracefully (`embeddings.available()` guards everywhere — no model → no stored vectors, scorer falls back to token-Jaccard exactly as before).
- **Deterministic scan** (`estate_scan.py`): provider-driven (`DiscoveryProvider.list_namespaces`/`list_relations`/`list_columns`) — **NOT** the LLM `data-discovery` skill. Scan-outcome states persisted per namespace + overall `EstateScan.state ∈ {completed, partial, failed}`; a probe preflights connection failure. **v1 scopes one connected database/catalog per source** (providers list schemas within one DB only). A deeper, PII-safe profiling pass (`profile_datasets`) is engineer-gated.
- **Evidence + verdict** (`feasibility.py`): **product-vs-raw separated** (published version-pinned products = green/adaptable pool via `enumerate_product_candidates`; estate datasets = assemblable pool). **Bipartite 1:1 assignment** of spec attrs → columns via new `schema_dna.score_matrix` (no double-counting). **Joinability** (shared identity keys) + derivability for assemblable/adaptable. The evaluator **skill decides the tier bounded by the deterministic heuristic CEILING** (`finalize_verdict`: a greener-than-evidence or product-less-green verdict falls back to the heuristic); **one tool-less call per domain batch** (cost boundary); heuristic fallback when the SDK is absent. `evaluation_state ∈ {completed, partial, insufficient_evidence}` is DISTINCT from the tier — **a partial/failed scan never yields a bare `absent`**. Runs stamp corpus/evaluator/skill/embedding/scan versions.
- **Tiered matching (schema shortlist → scoped column mapping).** A scan's schemas are unrelated functional areas (a `sales` and an `employees` schema may both carry a `product_id`), so Stage 1 matches each spec against the estate's **schema-level text** (`_schema_shortlist`, keyed by `(database, schema)`: enriched schema description [`_schema_descriptions` reads `EstateScan.enrichment_summary_json`] + table names/descriptions + a column sample, via `schema_dna.text_similarity` — embed-cosine with token-Jaccard fallback, embeddings precomputed once per run). The shortlist is **score-driven**, not a rank cap: a schema at/above `SCHEMA_SHORTLIST_THRESHOLD` (default 70 — the confident band) is shortlisted, up to `MAX_SCHEMAS_PER_SPEC` (default **5**) of them; `SCHEMA_RELEVANCE_FLOOR` (default 45) is the hard "is anything relevant at all" gate (a below-floor schema is ignored entirely, and Stage A is gated on the floor too so a pathological threshold<floor config can't admit one). **Best-one fallback:** when NOTHING reaches the threshold but some schema clears the floor, the single best floor-passer is still evaluated (marked `fallback=True`, low confidence) so a weakly-relevant estate grades instead of a false `absent`. Excluded rows carry structured reason codes — `below_floor` / `below_threshold` (clears the floor but not the confident band) / `over_cap` / `user_excluded`. Stage 2's `_raw_evidence` runs **only** over the in-scope datasets, so an unrelated schema can't produce false-positive column matches. Empty scope is therefore reached **iff** no schema clears the floor (same trigger as before the fallback); when it is (and no product covers the spec), the verdict is a clear `absent` with a "no relevant schema" rationale (`schema_scope_empty` rides `evidence_json` with all near-miss scores). Levers ride `EvaluateRequest` (`scope_to_schemas`/`schema_relevance_floor`/`schema_shortlist_threshold`/`max_schemas_per_spec`) → `FeasibilityRun.schema_scoping_json` → `evaluate_run`; `scope_to_schemas=False` restores whole-estate matching. **Recommend definitions**: `POST /api/feasibility/recommend-specs` reads the enriched estate (`build_estate_description`) and pre-checks which specs to evaluate — the `data-product-feasibility-recommender` skill with an always-available `heuristic_recommend` (embedding) fallback; bands `strong`/`tentative` mirror ResolveAndBind.
- **R2 entity/authority-aware column matching (`SCORING_VERSION="r2"`).** The scoped raw path (`_raw_evidence`) no longer scores columns table-blind. Each spec-attribute × candidate-column cell is re-ranked by `adjusted = (1-TABLE_AFFINITY_WEIGHT)·column_semantic + TABLE_AFFINITY_WEIGHT·table_affinity`, where **table_affinity is per-ATTRIBUTE** (`attr.name+concept+description` vs the table's `name+description`, with the product/domain only a **weak 15% prior** — a product-level affinity would bias every column toward the dominant entity and break cross-entity attrs like `transaction_date`). Above that, an inferred **FK-carrier** column (`_infer_fk_carrier`, camelCase/singular-plural aware — `customerID`/`CustomerId`/`customer_id`/`customerIdentifier`; the authoritative table's own key is never self-labeled) is docked `FK_CARRIER_PENALTY` when the referenced authoritative table is in scope AND itself carries a matching column — so `customer_id`→`customers.customer_id` beats the fact table's FK, and `name`→`customers.name` beats `suppliers.name`. Greedy 1:1 assignment is made **deterministic** (tie-break `(adjusted, column_semantic, dataset_uri, column)`); optimal max-weight matching is deferred. Rows keep separate score components (`column_semantic`/`table_affinity`/`adjusted`/`fk_role`) + `attr_id` (stable index-based id `#3:customer_id`, never a bare name) + per-attr `status ∈ {direct_match, derivable, missing, unknown}`. Structured `alternatives` (keyed by `attr_id`; ranked matched runners-up + gap near-misses, each with a `reason ∈ {chosen, below_threshold, type_incompatible, wrong_entity, fk_carrier, insufficient_evidence}`; the chosen candidate is always retained) ride `raw_candidates`. A **grain-key hard gate** (`_apply_grain_gate`, F-lite) caps a buildable tier to `absent` when any `spec.grain.keys` / required `is_key` attribute is unmatched (`heuristic_verdict(ev, scan_state, spec)`; `spec=None` skips it for unit callers). `_schema_shortlist` rows carry structured reason codes (`band`/`threshold_distance`/`description_source`/`excluded_reason`); `build_spec_evidence` adds `matched_tables` + a prose `rationale` per included row. **Schema-description robustness (Workstream A):** `estate_enrich._fallback_schema_description` fills a deterministic description on empty/parse-fail/partial enrichment; `enrichment_summary_json` gains `schema_description_source` (`llm`|`fallback`); `feasibility._resolve_schema_descs` adds a **read-time** synth so pre-provenance scans improve without re-enrichment, and `_schema_group_text` down-weights a `fallback`-sourced description (skips folding synthesized prose in as authoritative). **Live progress (Workstream B):** `FeasibilityRun.progress_json` (own short-lived-session `_persist_progress`, never entangled with score persistence) advances `shortlisting → building_evidence → evaluating → finalizing` (or `failed`); surfaced by `_run_row` + polled by `FeasibilityPage`. Run summary stamps the R2 scoring levers (`scoring_version`/`table_affinity_weight`/`fk_carrier_penalty`/thresholds). Deferred to R3: coherent joinable source-plan selection, profiling-based authority + real FK edges, full requirement-status taxonomy, optimal bipartite matching, and a full metrics/benchmark harness.
- **R3 composite-derivation engine + scan/add UX (`SCORING_VERSION` unchanged; catalog `catalog_version`).** Three shipped follow-ups:
  - **Composite derivations as first-class candidates (single reconciliation pass).** `_raw_evidence`'s greedy loop is now ONE candidate-merge pass over **direct** (above-threshold `(attr,col)`) + **composite** candidates — never a post-hoc mutation of finalized evidence. A composite satisfies an attribute by composing ≥2 columns of the **same table** per a curated `feasibility_derivations.DerivationPattern` (alias-structured `target_aliases` + a neutral `operator` + `components`, each with its own alias set + optional `type_family` gate). Component roles resolve **injectively** to distinct columns (`_resolve_components`: alias-equality is 100, `schema_dna` secondary, both ≥ `COMPONENT_MATCH_THRESHOLD=70`; `type_family` gates `compute`, e.g. `age_from_dob`'s `birth_date` must be temporal). A composite forms only on an **affinity-eligible** table (`affinity ≥ COMPOSITE_TABLE_AFFINITY_FLOOR=10`, else the top-affinity table). `composite_adjusted = (1-TABLE_AFFINITY_WEIGHT)·(0.7·component_min + 0.3·component_mean) + TABLE_AFFINITY_WEIGHT·affinity − DERIVATION_PENALTY=6`; the **penalty IS the replacement margin** — a composite supersedes a same-attr direct only by exceeding it by the penalty, a gap takes a composite uncontested. Reconciliation: a **direct** winner consumes its physical column (1:1), a **composite** consumes NONE (component columns stay reusable; a column freed by a composite win is reconsidered in the SAME pass — no stale state). Composition is **skipped for key/grain attrs** and the grain gate counts **direct-only** matches (`match_kind ∈ {direct, composite}`; belt-and-suspenders). The displaced direct pick is retained as an alternative with reason `superseded_by_derivation`; composite rows carry a `composite: {kind, operator, table, components:[{role,column,score}], source}` detail (`_collect_derivations` picks them up). **Catalog is loaded deterministically + fail-closed** (`feasibility_derivations.load_patterns` — one malformed entry rejects the WHOLE catalog and surfaces `derivation_catalog_error` in the run summary, never a silent empty). The **same skill** (`data-product-derivation-advisor`) produces run-scoped `ProposedDerivation`s, **gaps-only** (may only fill an unmatched required attr, never supersede a direct), validated **exact-ref** against that spec's supplied inventory (`_validate_proposals`: `unknown_column`/`mixed_tables`/`wrong_spec`/`type_incompatible`) + distinct-column + type gates before `evaluate_run` re-runs `build_spec_evidence(..., extra_proposals=)` for affected specs. Audited in `summary_json.derivation = {attempted, proposals_received/valid/applied, rejected_by_reason, catalog_version, catalog_error?}` + `attempted_derivation_skill`/`used_derivation_skill`. The catalog is GLOBAL (no edits to the 41 corpus specs). Deferred: cross-table/joinable composition, profiling-based key authority, a benchmark harness.

## SQL executor facade + Postgres view-recreate recovery

`sql_executor.py` is the **facade** — the single choke point for the safety gate (single-SELECT / CREATE-DROP-VIEW via sqlparse), row caps, read-only policy, the `:QueryRun` Neo4j audit, and mapping a provider's neutral `ResultSet`/`DeploymentRun` → `SelectResult`/`DeployResult`. It never opens a driver connection itself: `execute_select`/`execute_deploy` resolve the per-platform `QueryExecutor`/`DeploymentProvider` through the central lookup (`platform/dispatch.get_query_executor`/`get_deployment_provider`, fail-closed on unknown → `platform_not_supported`) and delegate. Postgres is one provider among peers; `import psycopg2` is lazy inside `PostgresQueryExecutor`/`PostgresDeploymentProvider`. A transient Postgres DSN rides a neutral `dsn` key on the connection_ref (no `pg_connection` shape); non-Postgres rides the structured `connection_ref`.

**View-recreate recovery lives in `PostgresDeploymentProvider.deploy_views`.** Postgres' `CREATE OR REPLACE VIEW` can ADD columns + CHANGE expressions but cannot CHANGE a column's data type or REMOVE columns. When the wizard's schema authoring drifts column types (e.g. `text` → `varchar(320)`), the redeploy hits this Postgres limitation. The provider's recovery path triggers on these specific error patterns:

- `"cannot change data type of view column"`
- `"cannot drop columns from view"`
- `"cannot change name of view column"`
- `"cannot change number of columns in view"`

On match, it opens a second transaction: `DROP VIEW IF EXISTS "<schema>"."<view>"` (NON-CASCADE) for every name in `view_names`, then re-runs the original DDL + smoke-tests. Non-CASCADE is deliberate — dependent objects surface as a distinct `dependents_block_redeploy` error class with a clear message rather than getting silently nuked. (The facade re-classifies a raw `sql_error` whose DDL carries an operator-less prose WHERE as `predicate_prose`.)

## DQ Rules: four sources

`:PropertyShape` lifecycle (`status: 'pending_review' | 'approved' | 'rejected'`):
- **`observation`** — auto-discovered by `data-quality-rule-generation` from profiling. Anchored to `:Column`. For SA, reviewed by PO in the validation gate; for `dq` archetype, reviewed by DQA.
- **`domain`** — generated from `playbook/domain_catalogs/{domain}.yaml`. Anchored to `:DProdColumn`.
- **`user`** — PO-authored via wizard chat assistant `applies_to: rule_create`. Auto-approved.
- **`spec`** — embedded in ingested ODCS `quality[]`. Materialised by `_materialise_spec_rules` inside `_generate_dprod`. Status = `'approved'`.

**Lifecycle by category.** Two buckets — categorise once, all downstream filters follow:
- **Author-asserted** (`user`, `domain` accepted in the wizard, `spec` from ODCS) → land at `status='approved'` on the authoring commit (wizard submit, ODCS ingest). The wizard pre-approves every catalog-suggested rule by default and the PO individually rejects what doesn't fit before submitting — the row-level Reject button moves a rule into `rejectedRules`; `finalize()` then approves the rest and rejects those. Domain rules created via the API endpoint OUTSIDE the wizard still land at `status='pending_review'` and use the standard `/reviews/domain_rules` queue.
- **Machine-discovered** (`observation` from profiling via `data-quality-rule-generation`) → land at `status='pending_review'`. Reviewed by PO in the SA validation gate (dpe-sa) or by DQA (dq archetype) before they affect downstream.

Downstream filters are aligned around `status='approved'`: marketplace Quality tab (`routers/marketplace.py` PropertyShape clause), DQ test generation (`data-quality-testing-gx` / `data-quality-testing-python` skills, both unscoped + scoped query variants), and the scoring `grounding` dimension (`data-scoring` skill). The engineer's DQ Rules summary card (`summary.py:DQ_RULE_COUNT`) intentionally counts ALL statuses per-source so triage state stays visible.

**DQ testing is dual-mode: `catalog` vs `dprod` (mirrors `data-mapping-neo4j`'s `--source-mode`).** (User-facing walkthrough: **`docs/data-quality-testing.md`**.) The same DQ stage IDs (`dq_test_generation_gx`/`_python`, `dq_test_execution`, `dq_failure_analysis`) run in one of two modes, chosen by the **workflow the stage runs in** (`stage_execution.resolve_dq_source_mode`: `product_dq_testing` → dprod, else catalog):
- **catalog** (default) — observation rules on `:Column`, executed against the source DB (resolved via the project's `SourceBinding` → `PlatformConnection`). Rule *generation* (observation-from-profiling) is catalog-only. Served by the `dq_testing` + `baseline_dq_rules` workflow groups.
- **dprod** — the new `_WF_PRODUCT_DQ` group (`workflow_id="product_dq_testing"`, **no `dq_rule_generation`**). The generators take `--source-mode dprod --target-contract {code}-contract --view-schema <schema>` and read contract rules on `:DProdColumn` (spec/domain/user) via `(dc)-[:MATERIALISES_AS]->(dp)-[:DPROD_OUTPUT_PORT]->…->(ods)-[:HAS_PRODUCT_COLUMN]->(pc)<-[:ON_DPROD_COLUMN]-(ps)`, keying tests to the deployed `vw_<safe_name(physicalName)>` views (`_safe_name` mirrors `generate_view_ddl.py` exactly). `dq_test_executor._resolve_dprod_conn_string` resolves the deployed-product connection via `pg_resolver.resolve_read_connection_for_consumer` (served-location-first: an SA product's own connection, or a CF product's `:CONSUMES`-borrowed connection reading from where the source was *materialized* — e.g. Databricks — per `8a06e42`) and **guards** on the served platform (not the origin) + `:ServingDefinition.deploymentStatus='deployed'`. Execution is no longer Postgres-only: every platform (Postgres included) gets its DSN from the resolved `SourceBinding`/served target via `build_connection_string`, gated by `_preflight_sqlalchemy_dialect` (a missing dialect → an actionable `pip install <pkg>` message instead of a subprocess crash; the generated GX runner is already multi-platform). An unrecognised served platform fails closed. SA and CF converge at test time; they differ only in the rule *seed* (SA derives→materializes onto `:DProdColumn`; CF authors directly).

**Archetype-conditional catalog** (`archetypes.get_workflow_catalog(archetype)`, feeds REST `list_catalog` + MCP `list_available_workflows`): `dpe-cf` sees `product_dq_testing` only (no `:Column` to test); dataset archetypes (`dq`/`dd`/…) see catalog DQ only; `dpe-sa` sees both (product primary + catalog pre-check). **Read parity:** `get_dq_rules` + the `dq_rules` detail card branch to `DQ_RULES_DETAIL_DPROD` for `dpe-cf` (product rules live on `:DProdColumn`), and the `dpe-cf` `dq_rules` dashboard card is no longer hidden.

**On-disk suite separation (`_dprod` suffix).** dprod suites are generated into `dq_tests_{gx,python}_dprod/` (catalog stays `dq_tests_{gx,python}/`), so a `dpe-sa` product holding BOTH a catalog pre-check suite and a dprod suite doesn't collide on disk and the executor's framework auto-detect tells them apart. `dq_test_executor.dq_subdir(base, source_mode)` is the single choke point — threaded through `dq_test_generator` (`output_dir`), `dq_test_executor` (`_FRAMEWORKS` subdir + `_detect_framework`), `stage_execution._dq_failure_context` (the failure-analysis dir), `dq_package` (`detect_active_framework`/`available_dq_suites`/`resolve_suite`/`collect_dq_files`/`assemble_dq_package`, all `source_mode`-aware), `serving_package.collect_for_git` (enumerates every present suite), and `routers/artifacts.py` (adds the `_dprod` results dirs). The `/dq-package` REST endpoint + MCP `get_dq_package` take an optional `source_mode` (auto-pick when omitted, dprod preferred); the frontend download button derives it from the stage's workflow (`product_dq_testing` → dprod), and the dprod zip is name-suffixed so both packages coexist in a downloads folder.

**Result-loader `:DProdColumn` linkage.** The GX loader (`data-quality-testing-gx/scripts/load_test_results_to_graph.py`) is `--source-mode`-aware: dprod results (whose embedded `meta.columnUri` is a `:DProdColumn` URI) anchor the `:TestResult` to `:DProdColumn` via `:ON_DPROD_COLUMN`; catalog stays `:Column`/`:ON_COLUMN`. The rule link (`:VALIDATES_RULE` → shared `:PropertyShape`) is mode-agnostic. The executor passes the flag in dprod mode; `routers/test_runs.py:_TEST_RESULTS_FOR_RUN` dual-anchors (coalesces `:Column`/`:Dataset` with `:DProdColumn`/`:DProdOutputDataset`) so per-column drill-down surfaces for either mode. (The Pandera framework has no loader script → graph load is a graceful skip in both modes, unchanged.)

**Wizard authoring on edit re-entry.** `/odcs/suggest-domain-rules` returns each rule's live `:PropertyShape.status` (from `PERSIST_SUGGESTED_RULE`'s RETURN — ON CREATE sets `pending_review`, ON MATCH leaves status untouched). Wizard's `advanceToRuleCoach` seeds `approvedRules` from anything not explicitly `'rejected'`. New products pre-approve all suggestions; re-opening a published product preserves prior PO decisions.

**Idempotent review actions.** `APPROVE_DOMAIN_RULE_QUERY` / `REJECT_DOMAIN_RULE_QUERY` gate the `SET ps.status` + `:ProvActivity` chain on `WHERE coalesce(ps.status, 'pending_review') <> '<target>'`. Re-applying the same status is a true no-op — matters because wizard re-submit blindly re-POSTs the entire `approvedRules` set.

**Marketplace dual-encoding caveat.** Each spec rule lives twice in the graph: as `:DataContractQuality` (verbatim spec severity) AND as a SHACL-shaped `:PropertyShape {ruleSource='spec'}` on `:DProdColumn` (severities translated to `sh:Violation` / `sh:Warning`). Marketplace `PRODUCT_DETAIL` deliberately excludes the `spec` PropertyShape so consumers see each rule exactly once; engineer-facing surfaces still see both copies.

DQ Rules summary card shows per-source bucket counts AND per-status counts (pending / rejected) via `summary.py:DQ_RULE_COUNT` (`coalesce(ps.status, 'approved')` for back-compat with legacy unstamped rules); `ProjectDashboard.tsx` renders subtitle `<sources> · <pending/rejected>`. Engineering detail + marketplace Quality tab share a collapsible accordion grouped by **table × category** (Structural / Value / Length / Other); categorisation in `frontend/src/lib/ruleCategory.ts`.

## Transformations

`:ColumnMapping` carries a structured DSL (concat / cast / lookup / case / arithmetic / literal / bucket / mask / hash / window / ...). `transformAuthor` mirrors the four-source DQ pattern: `po_hint` ↔ `spec`, `steward_catalog` ↔ `domain`, `engineer` ↔ `user`, `ai_suggestion` ↔ `observation`. Prompt enforces priority: hint → catalog → LLM.

**Raw `expression`-kind is dialect-translated at emit.** A raw `transformExpression` is authored in ONE grammar (usually the steward catalog's Postgres — `expressionDialect` defaults to `'postgres'`) but the product may be served on Databricks/Snowflake/BigQuery. `generate_view_ddl.py:_compile_select_expr` now runs `_translate_raw_expression` after `_substitute_inputs`, rendering the raw SQL to the target dialect via `dialect_sql.compile_expression` (consuming the `CompileResult.sql` the diagnostics pass already computed but previously discarded) — so e.g. a Postgres `REGEXP_REPLACE(..., 'g')` emits the Databricks 3-arg form instead of casting `'g'`→INT and failing. It activates **only cross-dialect** (same-dialect is byte-unchanged) and is **fail-open** (an unsupported/unknown function or any error leaves the expression verbatim; the capability diagnostics/preflight stay the enforcement surface). Structured kinds remain the robust path (they never depend on the transpiler). This closes the "verbatim raw-SQL emission" gap in `docs/architecture/transform-portability.md` for the `expression` kind; the other nested raw-SQL surfaces (lookup fragments, `filterPredicate`, join predicates) are still emitted verbatim.

The full model — per-kind `transformParams` schemas, view-DDL SELECT emission, the constant `literal` kind (no source edges), `lookup.selection_strategy ∈ {equi, latest, aggregate, exists}` with derived-join dedup, steward escalation flow, and the `column_transform_set` apply protocol — lives in **`docs/architecture/transformations.md`**. Open when working on `generate_view_ddl.py`, `TransformEditor.tsx`, or extending `VALID_TRANSFORM_KINDS`.

**`:LOOKUP_VIA` lineage edge.** A `lookup` transform's `lookup_table` / `value_column` / `key_column` live as **bare-name strings** in `transformParams` (no URI, no edge) — so the reference table it reads from (often a *different* CONSUMES'd source product than the mapping's primary `:MAPS_SOURCE_COLUMN` source) was historically invisible in lineage. It's now projected as `(:ColumnMapping)-[:LOOKUP_VIA {role, strategy}]->(:Column | :DProdColumn)`, `role ∈ {value, key}`. Created by `write_mappings.py` at authoring time **and** by the in-repo resolver `backend/lookup_via.py:reconcile_lookup_via` (auto-invoked on mapping approve/replace in `reviews.py`; one-shot backfill via `scripts/backfill_lookup_via.py --project-code <code>` — needed for products materialised before the edge shipped). Resolution strips a `schema.` qualifier + `vw_` override to the bare physical name, then matches `:Dataset.name` (catalog) or `:DProdOutputDataset.physicalName` reachable via `:CONSUMES` (dprod); unresolvable names are skipped (the DDL stays source of truth). **Case-insensitive since Tier 7:** the column/table side matches on `coalesce(searchName, toLower(name))` (a normalized `searchName = toLower(name)` property on `:Dataset`/`:Column`/`:DProdColumn`, populated on discovery/dprod-build + `scripts/backfill_search_name.py`), so an authored reference whose casing differs from the discovered identifier (e.g. Snowflake's UPPER-folded unquoted names vs a lowercased hint) still resolves. `write_mappings.py`'s `_RESOLVE_*_LOOKUP` and `lookup_via.py`'s `_RESOLVE_*_COLUMN` are the paired sites — keep them in sync. (Catalog-aware URIs — a `{database}` segment — remain a separately-scoped follow-up.) Read by `marketplace.py` (`LINEAGE_LOOKUP_QUERY` + `MARKETPLACE_LOOKUP_GRAPH_QUERY` + `MARKETPLACE_UPSTREAM_LOOKUP_QUERY` — the marketplace Lineage tab's opt-in upstream tier walks one hop up from `:LOOKUP_VIA` to raw catalog, a companion of `MARKETPLACE_UPSTREAM_GRAPH_QUERY` that stays a **separate** query rather than bolting onto the primary dual-OPTIONAL chain), `reviews.py:GRAPH_LOOKUP_QUERY`, and `summary.py:MAPPINGS_DETAIL`; `lookup_via.merge_lookup_graph_rows` is the shared payload fold. The edge is purely additive — no existing query changes behaviour unless it opts into the traversal. Full detail in **`docs/architecture/transformations.md`** → "`:LOOKUP_VIA` lineage edge".

## Dataset-level shape: `:DatasetTransform`

Schema-level peer of column-level `:transformHint`. One `:DatasetTransform` per `:DataContractSchema` (source of truth, survives `_generate_dprod`) plus a parallel copy on `:DProdOutputDataset` (read side, rebuilt on every `_generate_dprod` via `DPROD_COPY_DATASET_TRANSFORM`). Reserved fields locked since Phase 2; each phase activates more without a graph migration:

- `filterPredicate`, `dedupeJson` — Phase 2 (raw WHERE, ROW_NUMBER dedupe)
- `groupingKeysJson` + column-level `aggregateFunction` / `groupingKey` — Phase 3 (activates the `grouped` CTE)
- `joinsJson` — Phase 4 (explicit FROM/JOIN graph; bypasses FK inference; engineer-authored override wins on per-run basis)
- `scdPolicyJson` (`latest_only` synthesises a dedupe; `scd2` validates columns + optional `is_current`; `snapshot` synthesises a WHERE pinning to one point-in-time) and `suppressedColumnsJson` (drop columns from SELECT while keeping them in contract/lineage) — Phase 5
- `windowSpecsJson` + column `transformKind='window'` — Phase 6 (named windows referenced by column mappings, emit `<FN>(<arg>) OVER (...)`)
- Phase 7 dialect picker: `serving_virtual_view` stage has a `dialect` config field; `generate_view_ddl.py` selects a `PostgresDialect` / `SnowflakeDialect` / `DatabricksDialect` / `BigQueryDialect` / ANSI subclass for type-cast, hash, and REGEXP_REPLACE emission

View-DDL renders as CTE layers (`base` → optional `deduped` → optional `grouped`) on top of either explicit `joinsJson` or FK-inferred FROM. Per-view structured summary (`<output>.summary.json`) is persisted as `:ServingDefinition.summaryJson` and rendered by `ServingWarningsCallout` on the engineer dashboard's serving detail and the marketplace product detail's Serving tab.

Full reserved-field semantics, ODCS round-trip rules, view-DDL CTE assembly, every SCD lowering, suppressedColumns defensive cleanup, window-function emission, the Phase 7 dialect abstraction, and all the wizard / engineer authoring surfaces live in **`docs/architecture/dataset-transform.md`**. Open it when working on `generate_view_ddl.py`, the wizard's Shape step, `TransformEditor.tsx`, `routers/dataset_transform.py`, or adding a new SQL dialect.

## Serving mode: virtual view vs dbt-materialized

A product is served one of two ways, discriminated by `:ServingDefinition.servingMode`:

- **`virtual_view`** — `CREATE OR REPLACE VIEW` DDL deployed against the source Postgres; always fresh, no history. Fields: `ddl`, `viewSchema`, `viewNames` (JSON array), `targetPlatform`, `deployedAt/By/To`, `deploymentStatus/Error`. Authored by the `serving_virtual_view` stage, deployed by `deploy_virtual_view` (`routers/serving.py`).
- **`dbt_materialized`** — a real, runnable dbt project scaffolded on the backend, built into physical tables (and dbt **snapshots** for SCD2 history) on a target Postgres. Fields: `dbtMaterialization` (table/incremental/view), `targetSchema`, `dbtProjectPath`, `modelsJson` (per-model `ddl` + status), `summaryJson`, `buildStatus`, `builtAt/By`, `buildDurationMs`, `buildError`. Authored by the `serving_physical_copy` stage (`routers/materialization.py`). Both modes can coexist on one product; `servingMode` discriminates.

**One SQL core, two emitters.** The view path and the dbt path share the same compiler — `generate_view_ddl.py:_assemble_view_ddl` exposes a `select_body`; `generate_dbt_project.py` calls `generate_view_ddl.generate_dbt_models()` to reuse the per-dataset compiler for model bodies. The virtual emit wraps it in `CREATE OR REPLACE VIEW … AS`; the dbt emit wraps it in `{{ config(...) }} <select_body>` (+ a LIMIT guard for sample builds). The view SELECT is **byte-identical** between modes — joins, transform DSL, dialect, SCD lowering all resolve once in the shared core. Don't fork transform/join logic into the dbt path.

**The package IS the execution unit (load-bearing).** All three serving modes are executed by running a **packaged runner** as a subprocess — DWB never deploys/serves through a *separate* internal path; it kicks off the package's own `run.py` and reads the structured `run_result.json` the runner writes. The *same* package is what an engineer downloads and runs. Pieces:
- `serving_runners/` — deterministic, tested, **stdlib + driver only, NO `workbench.*` imports** runner scripts copied verbatim into each package: `run_deploy.py` (+ `_deploy_core.py`, ported from `sql_executor.execute_deploy` incl. the Postgres view-recreate recovery), `run_dbt.py` (wraps `dbt build`, normalizes `target/run_results.json`), `run_lakehouse.py` (`--mode export|query`; DuckDB ATTACH→COPY parquet + `catalog.duckdb` + a **valid `TransferBatch` v1** manifest — `operation_encoding=full_load`, NOT the old invalid `"transformed"`), and `_wb_runresult.py` (the `RunRecorder` that writes `run_result.json` + JSONL `run.log`).
- `serving_runtime.py` (backend) — `RunResult` model, `execute_package_runner(pkg, args, env, timeout)` (subprocess → parse; fail-open synthesized failed result), `build_runner_env(prefix, platform, connection_ref)` (→ `WB_*` env; **secrets ride the subprocess env, never disk**).
- `serving_package.py` — `assemble_{view,dbt,lakehouse}_package` + zip/collect utilities + `collect_for_git` (text-only file map for a git push); `serving_docs.py` — programmatic README via the `data-serving-view-documenter`/`data-serving-dbt-documenter`/`data-serving-lakehouse-documenter` skills (+ `migration-package-documenter` for the dmig migration package, via `migration_docs.py`) (JSON `{files}` verdict) with deterministic Python fallbacks. **README contract:** every package README (skill OR fallback) follows the same seven-section order per package type — title/what-this-is → **artifact inventory table** → **How it works** (orchestration mermaid: env + artifact → run.py → target) → **How the technology works** (the under-the-hood mechanics — a concise strategy-/platform-specific prose block + a *second* "under the hood" mermaid describing what the engine actually does: migration→warehouse *normalize→Parquet→stage→`COPY INTO`* vs →relational *direct load*; dbt *compile→run(per materialization)→snapshot*; lakehouse *DuckDB ATTACH→COPY→Parquet→verify*; view *zero-copy `CREATE OR REPLACE VIEW`*) → **Configuration** (env-var table, system-shell vs `.env`) → **Usage** (per-script commands + flag tables) → **Outputs**. The under-the-hood mechanics are grounded in a human-verified `reference/tech/*.md` corpus bundled per documenter skill and mirrored by `serving_package._tech_mechanics_section` so the fallback reads the same as the skill by construction. The `readme_provider` is wired into the *authoring* paths (`deploy_virtual_view`, full `materialize`, lakehouse export); `assemble_*` **preserves an existing README** on an *unchanged* re-assemble (a plain download) rather than clobbering a skill-authored one, writing the rich fallback only when none exists — BUT on a **regeneration** it clears the stale README first so the current skill/fallback rewrites it (`_invalidate_stale_readme` + `_artifact_changed`: view = `view.sql` DDL changed, migration = `migration.json` spec changed, lakehouse = `models.json` changed, dbt = a full authoring build i.e. `readme_provider` present). This is what lets a documenter/fallback improvement reach an already-authored package: it lands the next time that package's core artifact is regenerated (a plain re-download of an unchanged product keeps the existing README).
- Re-routed callers: `routers/serving.py:deploy_virtual_view`, `routers/materialization.py:materialize` (gate/persistence preserved), `lakehouse_export.run_lakehouse_export`.
- Download: `GET /serving/{view-package,lakehouse-package}?format=zip|json` + the enhanced `/serving/dbt-project`; MCP `get_view_package`/`get_lakehouse_package`; frontend "⤓ Download package" on completed serving stages (`Pipeline.tsx`) + the ProjectDashboard serving card (`lib/download.ts:downloadBlobZip`). `sql_executor.execute_deploy` is kept as legacy/reference (its tests still run) but the serving path no longer calls it.

**Uniform Configure → Build → Deploy (all three modes).** Every serving mode now shares the same three-step lifecycle the virtual path always had: **Configure Serving** (`configure_serving`, dialog-driven) → **Build** (the exclusive-group member — assembles the runnable, downloadable, git-pushable package with **no live-DB dependency**) → **Deploy** (a coupled non-LLM stage that executes the package against the real target/source). The Build stages are renamed `Build Virtual View` / `Build dbt Project` / `Build Lakehouse Package` (display names only — `stage_id`s are load-bearing and unchanged). Because Build completes without the DB, **Download package / Push to Git appear the moment Build finishes** — the package is no longer trapped behind a failing deploy.

| mode | Build stage (exclusive member) | Build endpoint (no DB) | Deploy stage (dependent) | Deploy endpoint (runs it) |
|---|---|---|---|---|
| virtual_view | `serving_virtual_view` | (LLM authors DDL + package) | `deploy_virtual_view` | `/serving/deploy` |
| dbt | `serving_physical_copy` | `POST /serving/dbt/build-package` (scaffold + assemble, no `dbt build`) | `deploy_physical_copy` | `/serving/materialize` (sample→full gate) |
| lakehouse | `serving_lakehouse_export` | `POST /serving/lakehouse/build` (`build_lakehouse_package`, assemble only) | `deploy_lakehouse` | `/serving/export` (`run_lakehouse_export`) |

`serving_transfer` (the 4th mode) is intentionally **not** split — it verifies inline and has no coupled deploy.

**Exclusive serving group.** The four `exclusive_group: "serving"` members in `archetypes.py` are the **Build** stages — at most one runs per product. Each Build member carries its coupled Deploy (and verify) via `EXCLUSIVE_GROUP_DEPENDENTS["serving"] = {"serving_virtual_view": ["deploy_virtual_view"], "serving_physical_copy": ["deploy_physical_copy"], "serving_lakehouse_export": ["deploy_lakehouse", "profile_parquet"], "serving_transfer": []}`. Selecting a member enables its Build+Deploy pair and disables every other member + their dependents. Switching goes through `POST /{project_id}/workflows/{workflow_id}/exclusive-group` → `switch_exclusive_group` (`routers/projects.py`). **`StageRun` identity is positional** — there is no `stage_id` column; a row is resolved by its `stage_number` index into the enabled-stage list. The switch reconciles StageRun rows in two passes: capture the pre-edit `stage_number → stage_id` map, flip the `workflow_json` enabled flags (dependents carried generically via `dependent_owner`), then re-key StageRun rows so completed stages keep their results, deselected rows are dropped, and newly-selected members get a fresh `pending` row. The MCP `set_serving_mode` tool wraps this. Deploy stages live in the `_WF_INTEGRATION` (dpe-cf) and `_WF_PRODUCT_MATERIALIZATION_SA` (dpe-sa) templates as `enabled: False` peers of `deploy_virtual_view`.

**Verification gate (materialized).** `POST /serving/materialize` (`mode=sample|full`, `sample_limit`, `force`) scaffolds + `dbt build`s. A **full** build is server-blocked unless a recent **sample** build passed (`gate_state ∈ {no_sample, awaiting_approval, built, rejected, sample_failed}`, from `GET /serving/materialization/status`); `POST /serving/materialization/reject` re-blocks. `force=true` bypasses the gate (the MCP path, which has no interactive preview). Timeouts: 300s sample / 1800s full. `MaterializationGateDialog.tsx` drives the sample → inspect preview → approve → full UX.

**No-secrets dbt project.** `profiles.yml` reads `WB_DBT_HOST/USER/PASSWORD/DBNAME` via `env_var()`; the backend injects them through the subprocess `env` (`_dbt_env()` parses the target DSN). So the scaffold is shareable without leaking credentials — which is why `GET /serving/dbt-project?format=zip|json` (and the MCP `get_dbt_project`) can hand the whole project to an engineer; `collect_dbt_files()` excludes `target/`, `logs/`, `dbt_packages/`. SCD2 `table→snapshot` transitions need `_reconcile_snapshot_targets` to drop a stale non-snapshot relation first (RESTRICT, not CASCADE).

**Per-product target connection.** `MaterializationTarget` (SQLite, keyed `contract_id = {project_code}-contract`) holds an optional dbt target — preferably a registered `PlatformConnection` via `target_connection_id` (the single connection contract), else a legacy inline config in `connection_json` (a transient Postgres DSN under a `dsn` key, or non-PG public config). There is no `pg_connection` field. `resolve_materialization_connection()` falls back to the source connection when unset. CRUD at `GET/PUT/DELETE /serving/materialization-target`; MCP `set_materialization_target`.

**Serving-strategy advisor.** `POST /serving-strategy/advise` (scoped: reads `:DProdOutputDataset`; unscoped: inline signals from the PO wizard) recommends virtual vs materialized. `_heuristic_serving_strategy` emits **required** drivers for SCD2 history and cross-platform source/target, **consider** hints for grouped/aggregated datasets and for **`productKind == 'aggregate'`** (an aggregate defaults to a materialized recommendation so downstream consumers borrow a real table instead of a fragile view-over-view — a *recommendation* that flips `recommended_mode` to materialized WITHOUT setting `required`, so a co-located aggregate may still choose virtual), else virtual. `product_kind` reaches the heuristic via the `AdviseBody.product_kind` field (unscoped/wizard) or `_resolve_product_kind_from_graph` (scoped). The optional `serving-strategy-advisor` skill may decorate the rationale but **must never flip `recommended_mode` or downgrade a `required` driver**. Surfaced by `ServingStrategyAdvice.tsx`; the PO's recommendation reaches the engineer via `ProductOwnerContextBanner` (`summary.py:PO_SERVING_QUERY`).

**Multi-hop serving read (`pg_resolver`).** A consumer with no direct connection borrows its read connection by walking `:CONSUMES` **recursively** (`resolve_source_connection_for_project`, deterministic upstream order, active edges only) — past intermediate virtual-view consumers to the first product with a real connection OR a materialized target (the nearest materialized boundary). `resolve_consumed_source_serving` builds the merged `--source-served-map` across all directly-consumed upstreams that share ONE physical connection (compared by **stable `connection_identity`** — host/db/instance, not just platform), covering both **materialized** upstreams (real tables at their target) and **deployed virtual-view** upstreams (`vw_<safe>` in their deployed `viewSchema`, on their resolved read connection). Cross-instance chains can't be federated into one view → the intermediate must be materialized (federation deferred). The view-DDL skill references a dprod source column via `_source_col_ref` (`_safe_name` for a dprod source, matching the upstream view's `AS {_safe_name(pc_name)}` aliasing) so a PO-authored CF `Mixed Case` column resolves. A multi-dataset aggregate/consumer upstream exposes no `:REFERENCES`, so it needs engineer-authored `:DatasetTransform.joins[]` (the corrected no-FK-path 422 says so — re-running `odcs_to_dprod` never helps a derived upstream); a single-dataset upstream needs no join.

`generate_view_ddl.py`'s dialect abstraction, transform-DSL compilation, lookup-join two-pass model, and FK bridge discovery are documented in **`docs/architecture/view-ddl-fk-bridges.md`** + **`docs/architecture/transformations.md`**; per-product dbt phases are tracked in the memory note `project_dbt_materialization.md`.

## Git integration (push serving artifacts to a repo)

A data product's serving package(s) are downloadable **and** pushable to a git repo — one repo per product, named after `project_code`, hosted on self-hosted **Gitea** or **GitHub**. Off by default; configured in **Settings → Git Integration** (`AppSettings.git_provider|git_base_url|git_token|git_org|git_auto_push`; the GET `/api/settings` response exposes `git_token_set` (bool), never the token itself).

- **`git_provider.py`** — `GitProvider` ABC + `GiteaProvider` (`/api/v1`, `token` auth) + `GitHubProvider` (`api.github.com`, `Bearer`). Both push via the Contents API (`PUT .../contents/{path}` per file, base64 body, existing-file SHA for updates), tag the last commit with the contract version, and `ensure_repo` (create org+repo if missing, falling back to the user-repos API). Stdlib + `httpx`, no `git` binary, no clone. `get_provider(settings)` → provider or `None` (unconfigured = disabled, never an error).
- **`serving_package.collect_for_git(project, settings)`** — the pushed file map: serving code under `serving/` (view), `dbt/`, `lakehouse/`; OKF `product.md` → **`README.md`** + `docs/datasets/*` (no quality/reflection); ODCS spec as **`odcs.yaml`**. **Text only** — parquet/duckdb binaries are excluded (repos hold artifacts, not data).

## Marketplace surfaces

`/api/marketplace` and `/api/marketplace/detail` return `product_kind` (`'source'` | `'aggregate'` | `'consumer'`). Surfaces: 3-way `ProductKindChip` (the single label authority), filter chips (All / Source / Aggregate / Consumer), `consumes[]` / `consumed_by[]` cross-references via `:CONSUMES` (now multi-hop-capable — a consumer may consume aggregate/consumer upstreams), Score-OSI-now button, lineage canvas (`MappingGraphView.tsx`). A soft **reclassify nudge** fires in the marketplace detail when a `consumer` product's `consumed_by` becomes non-empty (it's acting as an aggregate).

Two load-bearing gotchas to know before touching marketplace queries: the **listing must pin to the latest published/superseded contract version** (not `isCurrent=true`) to prevent in-flight drafts from leaking into the consumer view, and **dprod nodes are not versioned** so `NewProductWizard.ensureProjectAndSaveSpec` skips `/generate-dprod` when hydrating a published **or approved** product.

**Layered value-flow ("Sankey view") — `GET /api/marketplace/flow`.** Additive; the existing lineage views are untouched. Emits one normalized, context-agnostic `FlowPayload` — ALWAYS 5 columns in fixed order (`source_system`, `source_aligned`, `aggregate`, `consumer`, `use_case`) + `links` (`consumes` / `source_binding`; `supports` / `feasibility_match` reserved for the estate fast-follow) — assembled by the **pure, DB-free** `backend/flow_payload.py` (`FlowBuilder`: idempotent `add_node`, cross-column-reuse reject, `(source,target,kind)` link dedup, `build()` drops dangling links; `bucket_product_kind`: blank/unknown → `source_aligned`). Three reads: **middle three columns + `consumes`** = `FLOW_PRODUCT_NODES` (= `PRODUCT_LINEAGE_NODES` **plus a required row-level `WHERE cv.lifecycleState IN ['published','superseded']`** — a SEPARATE constant so `/product-lineage` is byte-unchanged; without the added guard the base query leaks never-published drafts via its OPTIONAL-MATCH fallback to `dc.currentVersion`) + `PRODUCT_LINEAGE_EDGES` (reused verbatim); **leftmost "Source Schemas"** = `FLOW_SOURCE_SYSTEMS`, a marketplace-wide generalization of `LINEAGE_QUERY`'s catalog arm, grouped by the **project-scoped `:Catalog` node** (`catalog:{project_code}:{schema}`) so a Postgres `public` shows once per project, `meta.synthesized=true`; **Use Cases** = pure placeholder (VERIFIED: the live `_generate_dprod` never writes `keyUseCases`, so no read — the frontend renders one ghost node). Optional `?domain=` scopes products in Python (the builder drops links into filtered-out nodes). Counts: source node = # products fed; product node = # direct downstream `:CONSUMES` consumers. Frontend: `components/flow-sankey/` (fixed-column React Flow, NOT d3-sankey) mounted as the **Sankey view** sub-tab in `MarketplacePage.tsx`. Tests: `tests/test_flow_views.py`. Full detail (incl. the honest gaps) in **`docs/architecture/marketplace.md`**. Pinning is over the versioned `:ContractVersion` model — `head(collect(cv_pub)) ORDER BY cv_pub.version DESC` filtered to `lifecycleState IN ['published','superseded']`, fallback `coalesce(cv_deployed, cv_cur)` keyed on `dc.currentVersion` (NOT the old `lifecycleVersion`/`isCurrent`). The pinning Cypher, the leak-mitigation guard, and all UI surface wiring live in **`docs/architecture/marketplace.md`**.

**OKF export (Open Knowledge Format).** `okf_export.py:collect_okf_files(settings, uri=None)` projects published products into an OKF v0.1 bundle — markdown docs with YAML frontmatter, cross-linked by `:CONSUMES`. `uri` given → single-product bundle (`product.md` + `datasets/*` + `quality.md` + optional `reflection.md`); `uri` omitted → whole-marketplace bundle (`catalog.md` + `products/<code>/…`, cross-links resolved to bundle-relative paths). It's a deterministic, **lossy-by-design** projection: it reuses `marketplace.PRODUCT_DETAIL` + `_shape_detail` (so it tracks the marketplace shape exactly) and recovers OKF's untyped links by stating each relationship in prose AND a custom `relationship:`/`consumes:` frontmatter key. Reserved filenames (`index.md`/`log.md`) are deliberately avoided for trivial v0.1 conformance. Exposed at `GET /api/marketplace/okf-bundle` + `GET /api/marketplace/products/{contract_id}/okf-bundle` (`?format=zip|json`, `routers/okf.py`, mirroring the dbt-project export) and the MCP `get_okf_bundle` tool. Framing: a portable *briefing* for external agents that can't reach our MCP/graph — complements ODCS (the contract) and the dbt project (runnable); never a default pipeline stage.

## Semantic layer & marketplace chat

A cross-product business-concept layer on top of deployed views, curated by the Data Steward and consumed by marketplace Q&A. Full model in **`docs/architecture/semantic-layer.md`**.

- **`:BusinessConcept`** is a 3-tier tree (`entity` → `attribute` → `value`; legacy `super` is coalesced to `attribute`), with predicate templates + column/dataset bindings (`:REPRESENTED_BY`) + a `:RELATES_TO` join graph. Edges: `entity-[:HAS_ATTRIBUTE]→attribute-[:HAS_VALUE]→value`; entities bind to `:DProdOutputDataset`, attributes to `:DProdColumn`, values carry a `value_token`. `business_concepts.py` is CRUD + queries; `entity_scaffolding.py` is the deterministic scaffold; the `business-concept-advisor` skill enriches; `concept_svg.py` renders the tree SVG.
- **Discovery sequence** (`semantic_discovery.py`) — the consolidated, domain-scoped way to *build* the layer, run in order: **scaffold** (deterministic entity/attribute/value spine + bindings + FK `:RELATES_TO` from schema) → **recommend** (cross-product LLM advisor via `semantic_recommender.py`; auto-promotes proposals at/above a confidence threshold — default 0.7 — into bound + parented attributes, queuing the rest) → **enrich** (LLM polish of names/definitions/synonyms). `reset` soft-deprecates the domain first for a clean rebuild. Each step writes a `:SemanticDiscoveryRun` (per domain+step: status, last-run, stats, a data-product **source fingerprint** for staleness, and `upstream_rerun` staleness when an earlier step re-ran). **Stranded** concepts (entity w/o dataset, attribute w/o column, value w/o parent) are surfaced, never auto-deleted. Auto-promote parents each attribute under the entity bound to the **same dataset as its evidence columns** (`semantic_discovery._RESOLVE_ENTITY_VIA_EVIDENCE`), so recommend must run *after* scaffold. The data-product layer is READ-ONLY throughout — writes touch `:BusinessConcept` (+ edges) and the run sidecar only.
  - **Tier-aware collision (load-bearing — don't regress).** Concept name-collision resolution in `business_concepts.create_concept` is decided by the pure `_collision_action(dup_level, new_level, if_exists)`: **never deprecate a HIGHER tier** (entity > attribute > value) — a same-named lower-tier creation *coreferences* the existing higher tier instead. This is why recommend (which promotes `level="attribute"`) can no longer clobber a scaffolded entity of the same name (the "Employee vanished" bug). `_DUP_CHECK` returns `level`; child-migration is gated to same-tier replaces. `_norm_name`/`_singularize` add singular/plural + case coreference (`Employees`→`Employee`) — **coreference-only, never destructive**. Recommend stats surface `coreferenced` + `deprecated_existing`; the stranded validator also flags an active attribute/value whose only parent is deprecated.
  - **Cross-product entity coreference (Phase A).** `entity_scaffolding._apply_cross_product_bindings` binds a consumer product's dataset to the SAME in-domain entity as the source dataset it maps to — anchored ONLY on provable `:ColumnMapping` lineage (`MAPS_TO_PRODUCT_COLUMN`←consumer, `MAPS_SOURCE_COLUMN`→source `:DProdColumn`), strict-majority per consumer dataset (junction/tie left unbound → no over-merge). Entity stays in-domain (NOT moved to `shared`); reported as scaffold `cross_product_bindings`. Deferred: `shared`-domain generalization beyond Country (Phase B) and cross-*platform* multi-binding query resolution (Phase C).
- **Embeddings** (`embeddings.py`): fastembed (CPU-only) vectors stored on a Neo4j vector index — no external embedding service. `embed_documents` is backed by a **persistent content-addressed cache** (`EmbeddingCache` SQLModel, keyed `sha256(MODEL_NAME + text)`): a text embedded on any prior run — or before a restart — is served from SQLite instead of re-encoded (transparent; no caller signature change; a fully-cached batch needs no live model). This covers the static feasibility spec corpus, per-run schema/affinity texts, and value-resolution. First-class graph nodes keep their vectors ON the node instead (`:BusinessConcept.embedding`, `:EstateColumn.embedding`); the cache is the residual store for everything that isn't a node.
- **Endpoints:** `routers/semantic.py` (`/api/semantic/*`) for concept CRUD + the discovery sequence (`GET /discovery/status`, `POST /discovery/run` {scaffold|recommend|enrich}, `POST /discovery/reset`) + the standalone recommend/accept queue. Marketplace **Semantic Q&A** at `POST /api/marketplace/chat` (`marketplace_chat.py` + `marketplace-product-chat-assistant` skill) answers a free-form NL question across a domain's deployed views as a single grounded SELECT. Two **retrieval modes**: `full` (all domain entities → model) and `concept_guided` (embedding-retrieve a relevant subset + 1-hop neighbours; falls back to full on a miss). Both echo `retrieval_mode` + `concepts_in_context` + `concepts_used` + a per-question `token_usage`; the UI renders a self-explanatory badge + an **Explain trace** panel (decompose → match → resolve → **ground_values** → generate_sql → execute). The MCP `query_semantic_layer` tool wraps this. **Dialect-aware execution:** the NL→SQL skills emit *standard/ANSI* SQL and `dialect_sql.render_for_platform` (sqlglot: parse→neutral AST→target dialect) renders it to the served engine (backticks for MySQL, etc.) **only at the LLM-generation sites** (never inside `sql_executor.execute_select`, whose samplers are already target-dialect via `sql_ident.quote_relation`); the allow-list runs on the pre-render SQL, and the executed SQL is surfaced in the trace. Per-view platform is recorded so a question spanning >1 platform returns a clean `cross_platform_unsupported` (federation is future work). `MarketplaceGap` logs consumer-reported gaps. A third **`conversational`** mode (server-side sessions, ontology-grounded router → query/clarify/reject/chat) sits above the two retrieval modes. **Instance value resolution** (record-level lookups — "where does John Doe live?") runs inside `answer_question` between concept matching and SQL generation: a value mention that isn't a `:BusinessConcept` is probed against live data (probe-first, data-decides; hybrid pg_trgm/prefix-ILIKE+rapidfuzz) and either grounded as a verified literal (`grounded_values`, injected into the NL→SQL skill) or returned as `needs_disambiguation` candidates. Full detail in **`docs/architecture/value-resolution.md`**.
- **Steward UI** (`SemanticRecommenderPage`) has three tabs: **Discovery** (the run-sequence home — step cards with status/last-run/staleness, Clear action, stranded validation panel), **Concepts** (manual CRUD + the diagram), **Review Queue** (triage proposals queued below the auto-promote threshold). MCP siblings: `get_semantic_discovery_status` / `run_semantic_discovery_step` / `reset_semantic_discovery` (domain-scoped, role-gated to Steward / Engineer / PO) let engineers drive the sequence headlessly.

## OSI scoring & QA evaluation

Producer-side **AI-readiness**, distinct from the DQ quality score. Detail in **`docs/architecture/data-product-scoring.md`** + **`docs/architecture/qa-and-reflection.md`**.

- **OSI** (`osi.py`, `routers/osi.py`): a predicate/rubric model — `score_rubric()` runs `PREDICATE_REGISTRY` predicates against the product's semantic model + validation report, assigns a RAG band (`WEIGHTS`, GREEN/AMBER thresholds), and persists `:OsiEvaluation` via `[:HAS_OSI_EVAL]`. Rubrics live in `playbook/scoring_rubrics/`. `score_osi()` is a back-compat shim. The `data-product-osi-advisor` skill writes the narrative + Apply cards (`osi_*` in the Apply protocol).

## LLM token accounting

A single append-only ledger of LLM token usage across every SDK call. `llm_usage.py`: `extract_usage(message)` normalizes the SDK `ResultMessage.usage` dict (the installed `claude_agent_sdk` exposes `usage` + `model_usage` + `total_cost_usd`); `UsageAccumulator` sums across passes; best-effort `record_usage(...)` inserts one `:LlmUsageEvent` SQLModel row (SQLite). **`total_tokens` = working tokens (uncached input + output)**; `cache_read_tokens` / `cache_creation_tokens` are tracked in their own columns and deliberately kept *out* of the total (skill-driven calls carry large, near-constant cache that would otherwise swamp the figure). Best-effort throughout — accounting never raises into an LLM feature, and tokens stay reliable even when `total_cost_usd` is `None` (Foundry).

- **Capture sites** — every `ResultMessage` handler funnels usage through `record_usage`: pipeline stages (`sdk_runner` → persisted in `stage_execution.py` / `routers/cli.py`, attributed by `project_code`), engineer + product chat, marketplace Semantic Q&A (summed across its 2–3 passes via a `contextvars` accumulator — `marketplace_chat.begin_qa_usage()` + `_note_usage`; tagged `domain` + `retrieval_mode`), and the one-shot advisors (osi / qa / qa_executor / filter_intent / ingest classifier+gap / schema+discovery advisor / serving_strategy / rationale_summarizer / deployment_reflection / semantic_recommender — recorded global-only, since their helpers don't carry product context).
- **Rollups** (`routers/usage.py`): `GET /api/usage/summary[?project_code|domain]` (totals + `by_source`), `GET /api/usage/by-project/{id}` (resolves id→code), `GET /api/usage/semantic-qa[?domain]` (grouped by `retrieval_mode` — the aggregate Full-vs-Concept comparison). UI: a global "LLM Token Usage" card on `SettingsPage`, a per-product token strip on `ProjectDashboard`, and per-question `N tok (in/out)` in the `MarketplaceChatPanel` answer footer + retrieval badge.

- **Auth is plain static bearer** (`WB_MCP_TOKENS`) — NOT OAuth. Token format is now **4-field**: `token` / `token:principal` / `token:principal:proj1|proj2` / `token:principal:projects:role`, where `role ∈ {owner, engineer, viewer}` (`viewer`/`readonly` ⇒ a read-only token). Missing 4th field → `role=None`, unrestricted (fully back-compatible with 1/2/3-field tokens). `_BearerAuthMiddleware` enforces per-principal project authorization and stashes `role` + `read_only` in `_auth_ctx`; `_deny_write()` (folded into every write tool) refuses when the instance is globally read-only (`WB_READ_ONLY`) **or** the token is a viewer token; `_role_guard` prefers the token's bound role over the self-declared param. `WB_MCP_ALLOW_INSECURE` is the fail-closed escape hatch. A path-rewrite middleware handles the bare-`/mcp`→`/mcp/` (and `/po-mcp`→`/po-mcp/`) 307 that broke static-bearer clients (Codex).
- **Review tools carry an acting `role`** — the server enforces the same per-surface role gate as the UI; re-call with the required role to "switch hats". Agentic `run_stage` shares the pipeline's `build_prompt` + `sdk_runner`; the MCP path uses a no-op message sink (no WebSocket).

## Authentication & authorization

Request-level auth for the REST API + WebSockets (the MCP endpoints kept their own bearer model — hardened above). **Gated** — enabled iff `WB_AUTH_SECRET` is set (or `WB_AUTH_REQUIRE=1` to fail-closed); unset → auth disabled + a startup warning, so local dev is unchanged. Full env/seed/OIDC-seam reference in **`docs/auth.md`**.

- **`auth.py`** — the core. `AuthUser` (`email`/`name`/`role`); `AuthProvider` ABC (the pluggability seam — `StaticUserProvider` now against the `AppUser` table, an `OIDCProvider` later without touching call sites); pbkdf2 password hashing (stdlib — no bcrypt/native dep); HS256 session JWTs via PyJWT (`issue_token`/`decode_token`, TTL `WB_AUTH_TOKEN_TTL_HOURS` default 12h); the `current_user` FastAPI dependency (reads `request.state.user`; returns a dev `engineer` when auth is off).
- **`authz.py`** — two server-enforced **account roles**: `owner` (Data Product Owner) and `engineer`. An `engineer` account still assumes the engineer-side hats (Steward / DQA / Reviewer) *client-side*; the server enforces only the PO↔Engineer boundary. `role_can_run_stage` / `role_can_review` (collapse the `types.ts` matrices to the two roles), `CLIENT_HATS_FOR_ROLE`, and the `require_role(...)` dependency factory. Shared by REST + MCP (parity is a hard requirement).
- **`AppUser`** SQLModel (`email` PK, `name`, `password_hash`, `role`, `active`) — new table, auto-created, no `_migrate()` ALTER. Seeded via `scripts/seed_users.py`.
- **`routers/auth.py`** (`/api/auth`): `POST /login` → `{token,email,name,role}`; `GET /me` → user + `client_hats` + `read_only`; `POST /logout` (stateless); `GET /config` (unauthenticated — the SPA reads it before it has a token).
- **Middleware** (`main.py`, next to `_normalize_mcp_slash`): one `@app.middleware("http")` (`_auth_and_readonly`) that (1) in **read-only mode** blocks any non-`GET`/`HEAD`/`OPTIONS` `/api/*` call (allowlist `/api/auth/login`) with `403 {read_only:true}`, and (2) when auth is enabled verifies the Bearer JWT for `/api/*` (allowlist `/api/health`, `/api/auth/login`, `/api/auth/config`; OPTIONS skipped for CORS preflight), setting `request.state.user`. CORS is registered **last** (outermost) so error responses carry CORS headers. Kit/bootstrap installers are authenticated by default. WS auth (`ws_authenticate` in `routers/websocket.py`, reused by chat/product-chat) verifies the `?token=` param before `accept()`, closing 1008 on failure; read-only additionally rejects the mutating WS actions.
- **Choke-point enforcement**: `stage_execution.start_stage_run(..., acting_role=)` (shared by WS + MCP `run_stage`) + `cli.py` stream enforce `role_can_run_stage`; the `reviews.py` POST handlers use `Depends(require_review(<type>))`; a few unambiguous routes use `Depends(require_role(...))` — serving/materialization = `engineer`; `osi/evaluate` + `odcs` publish = `owner`. Finer stage-level gating (which engineer hat) stays client-side (`canRunStage`), now driven by the authenticated account role.
- **`WB_READ_ONLY`** (live-read via `config.read_only()`) — a single global flag that blocks every mutation for everyone (REST 403, WS reject, MCP `_deny_write`) and drives the frontend banner + disabled controls. The primary safeguard for a hosted/shared demo box; flips without a restart.
- **Frontend**: `authStore.ts` (module singleton, `localStorage["workbench.auth"]`) shared by React (`AuthContext` via `useSyncExternalStore`) and non-React code (the axios interceptor attaches the bearer + routes to `/login` on 401 / toasts on read-only 403; `wsUrl()` appends `?token=`). `LoginPage` + `<RequireAuth>` in `App.tsx` (pass-through when auth off); the client `Role` context is seeded from the account role; `ProductShell`/`EngineerShell`/`PersonaChooser` gate to the role's shell. `useReadOnly()` drives the banner + disables the Pipeline Run control. `VITE_API_BASE` makes the backend origin env-overridable. Faked identity constants (`CURRENT_USER_EMAIL`/`CURRENT_ENGINEER`/`"workbench-user"`) are replaced by `useCurrentUserEmail()` so provenance reflects the logged-in user.

## Skills (`workbench-skills/` plugin)

**Vendored in-repo** as a Claude Code plugin at `workbench-skills/` (`.claude-plugin/plugin.json` + `skills/<name>/`; ~44 skills, version-controlled, baked into the backend image via the Dockerfile `COPY . .`; `config.py:SKILLS_DIR = BASE_DIR / "workbench-skills" / "skills"`). Each skill has `SKILL.md` + optional `scripts/` (Python). All Neo4j-querying scripts support `--project-code`.

**Why a plugin (not `.claude/skills/`)?** Anything under `<repo>/.claude/skills/` is auto-discovered as a slash command by the interactive Claude Code session used to *develop* the Workbench — the exact same discovery the backend SDK uses. The backend loads them explicitly: `config.PIPELINE_PLUGINS` (`[{"type":"local","path": <abs workbench-skills>}]`) is threaded into every `ClaudeAgentOptions(skills="all", plugins=PIPELINE_PLUGINS, …)` call site (`sdk_runner.py` + the ~13 programmatic skill callers). Skills resolve by **bare name** (e.g. `data-discovery`) — the plugin namespace is not required in prompts — and `${CLAUDE_SKILL_DIR}` still resolves to each skill's own dir. **When adding a new SDK call site, include `plugins=PIPELINE_PLUGINS` or the agent's Skill tool finds nothing.**

## Skill / chat reflection

`scripts/reflect_on_skills.py` ingests `StageExecution` rows for one skill and renders a markdown bundle (metrics, current SKILL.md, prompt_templates, per-run summaries with tool sequences + heuristic "wandering" flags). The `skill-reflector` skill consumes it and writes proposals to `playbook/skill_reflections/<skill>_<YYYY-MM-DD>.md`. Trigger: "reflect on skill X". Never auto-edits SKILL.md or archetypes.py.

`scripts/reflect_on_chats.py` is the chat sibling: ingests `ChatSession` + `ChatMessage`, attaches workflow snapshots, flags `bash_exploration` / `cypher_calls_unscoped` / `forbidden_*`. Reasoning half is `chat-reflector`; report goes to `playbook/chat_reflections/<YYYY-MM-DD>.md`.

## Project directories + config

Projects are `{archetype_prefix}-MMDDYYYY-NN` under `projects/`. Each contains `workflow.json`, `data_discovery/`, `data_profiling/`, `metadata/`, `cypher_scripts/`, `remediation/`. Passed as `cwd` to the SDK. Most config lives in `config.py`, but key values are **env-overridable** for containers: `WB_DATABASE_URL`, `WB_FRONTEND_URL`, and the LLM-auth vars (`ANTHROPIC_API_KEY` for the direct route; `ANTHROPIC_FOUNDRY_API_KEY` / `_RESOURCE` / `_MODEL` for Azure Foundry; `CLAUDE_CODE_OAUTH_TOKEN` for a workstation's own Claude Code **subscription** — a 1-year token from `claude setup-token`, the only subscription route that survives containerisation since the backend container has no `~/.claude`; precedence Foundry > API key > OAuth token). DW does **not** assume Azure — nothing is armed unless the Foundry key is set, in which case `config.py` flips `CLAUDE_CODE_USE_FOUNDRY=1`, routes LLM calls through Foundry, and pins all four model tiers to `ANTHROPIC_FOUNDRY_MODEL` (default `claude-opus-4-8`); otherwise auth is left entirely to the Agent SDK. **`ANTHROPIC_FOUNDRY_RESOURCE` is required and has NO default** (it names one tenant's private Azure resource) — a Foundry key without it logs an error at import and is a hard `dwb doctor` failure. Every one of these vars is read blank-tolerantly and must be forwarded on the compose `backend` service, or a `.env` value never reaches the container. Container compose secrets live in a gitignored `.env`; the committed `.env.example` is the template. Neo4j connection details stored per-project + globally in `AppSettings`.

## Tests

A focused pytest suite at `workbench/backend/tests/` (run from the repo ROOT so `workbench.backend.*` imports resolve). Self-contained: `conftest.py` points the SQLModel engine at a throwaway SQLite file and boots MCP in open mode BEFORE importing the backend, so NO Neo4j/Postgres is needed.

Test files: `test_acceptance_gate.py` (the shared request_guard lifecycle, REST + MCP), `test_mcp_parity.py` (UI/MCP behaviour parity), `test_view_ddl_bridges.py` (FK-bridge + SCD as-of view generation + the lookup transform DSL), `test_join_preflight.py` (disconnected-component detection), `test_marketplace_views.py` (marketplace projection + latest-version pinning), `test_semantic_conversation.py` (conversational Semantic Q&A router), `test_value_resolution.py` (instance value-resolution matcher), `test_docs_consistency.py` (**docs-drift guard** — fails when the MCP tool count quoted in docs diverges from the live `@mcp.tool()` count, when a retired graph term like `ON_PRODUCT_COLUMN` resurfaces, when a superseded property is presented as current, when `notes/`-style dead paths reappear, or when a requirements file pins `claude-code-sdk` instead of the `claude-agent-sdk` every backend module imports. Extend `RETIRED_HARD` / `RETIRED_SOFT` there when you rename a graph property or relationship. Dated audit docs + `research/` are exempt — they're historical snapshots).

Dependencies are pinned in `workbench/backend/requirements.txt` (`pytest>=8.0`, plus `fastapi`, `uvicorn`, `sqlmodel`, `sqlalchemy`, `websockets`, `aiofiles`, `neo4j`, `claude_agent_sdk`, `pyyaml`, `sqlglot`, `sqlparse`, `jsonschema`, `pandas`, `pandera`, `great-expectations`, `psycopg2`).
