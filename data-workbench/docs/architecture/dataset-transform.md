# Dataset-level shape: `:DatasetTransform` (Phases 2–7)

> **Read on demand.** The high-level summary lives in `CLAUDE.md`. This doc carries the per-phase reserved-field semantics, view-DDL CTE assembly, SCD lowering rules, window-function emission, and the Phase 7 dialect picker. Open this when you're working on `generate_view_ddl.py`, the wizard's Shape step, `TransformEditor.tsx`, `routers/dataset_transform.py`, or adding a new SQL dialect.

Schema-level peer of column-level `:transformHint`. One `:DatasetTransform` per `:DataContractSchema` (source of truth, survives `_generate_dprod`) plus a parallel copy on the corresponding `:DProdOutputDataset` (read side, rebuilt on every `_generate_dprod` via `DPROD_COPY_DATASET_TRANSFORM`). Reserved field shape locked since Phase 2 — each phase activates more fields without graph migration:

| Property | Phase | Notes |
|---|---|---|
| `filterPredicate` | 2 (active) | Compiled SQL fragment applied as `WHERE` on the base CTE. Authored either by interpreting `filterIntent` (PO prose → grounded SQL via the `filter-intent-interpreter` skill / heuristic at `/api/filter-intent/interpret`) or finalized by the engineer in the Filter Review panel (`PUT /dataset-transform/filter`). A shared safety gate (`sql_executor.validate_predicate` / `looks_like_prose`) refuses operator-less prose at the engineer PUT, at view-DDL generation (parse-only → `ViewGenerationError`), and at deploy (re-classifies the Postgres `sql_error` to `predicate_prose`), so plain language can never reach a deployed `WHERE`. |
| `filterIntent` | (this change) | The PO's plain-language row filter ("active employees only"). View-DDL **NEVER** reads it — it exists only as the human-readable source of `filterPredicate` and is shown read-only in the engineer's Filter Review panel. **Legacy-compat rule:** the canonicalizer never auto-derives one of `filter`/`filterIntent` from the other — a legacy product with `filter` (SQL) and no intent round-trips unchanged; a product with intent but no compiled predicate is caught by the safety gate. MCP parity: `get_dataset_filter` / `set_dataset_filter` + a `get_plan_summary` advisory. |
| `dedupeJson` | 2 (active) | JSON `{keys: [product_col, ...], order_by: product_col, direction: 'asc'\|'desc'}` |
| `groupingKeysJson` | 3 (active) | JSON list of product column names; activates the `grouped` CTE layer |
| `joinsJson` | 4 (active) | JSON list `[{alias, dataset_uri, kind, predicate}, ...]`; explicit FROM/JOIN graph |
| `windowSpecsJson` | 6 (active) | JSON dict `name → {partition_by[], order_by:[{column,direction}], frame}`. Referenced by column-level transforms with `kind='window'` to emit `<FN>(<arg>) OVER (<window>)` SQL |
| `scdPolicyJson` | 5 (active for `latest_only` + `scd2` + `snapshot`) | `{type, effective_column, expiration_column, natural_key[], add_is_current, snapshot_column, as_of_date}`. `latest_only` synthesizes a dedupe; `scd2` validates columns + optional `is_current` derivation; `snapshot` synthesizes a WHERE filter pinning the view to one point-in-time |
| `suppressedColumnsJson` | 5 (active) | JSON list of product-column names; dropped from the final SELECT (column still in contract / graph for lineage) |

**Column-level aggregation** (Phase 3, on `:ColumnMapping`):
- `aggregateFunction`: `SUM` / `COUNT` / `AVG` / `MIN` / `MAX` / `COUNT_DISTINCT` / `FIRST` / `LAST` — no-op unless the product dataset has `grouping_keys` set
- `groupingKey`: boolean — true marks the column as a GROUP BY passthrough rather than an aggregated value

**ODCS round-trip** (`odcs.py:_canonicalize_dataset_transform`): each schema entry may carry a peer-of-`properties` `transform` block. Accepts `transform` (canonical) and `x-workbench-transform` (extension-namespaced alias). camelCase keys (`groupingKeys`, `orderBy`, `datasetUri`) are lowered to snake_case. `joins[]` entries normalised to `{alias, dataset_uri, kind, predicate}`; kind defaulted to `'left'` if missing or invalid; malformed entries silently dropped. Materialisation back to YAML drops empties so contracts without dataset-level shape stay terse.

**View-DDL** (`generate_view_ddl.py:_assemble_view_ddl`): CTE layers activate independently. When `joins[]` is set, the FROM-clause assembly is built from the explicit declarations and FK discovery is bypassed entirely (`_build_from_explicit`); otherwise the FK-driven inference path runs (`_build_from_fk_inferred`). Explicit joins are emitted as authored with ONE overlay: a LEFT/INNER-joined **SCD satellite** (`is_current` flag or effective-dating `from/to` pair — `_satellite_needs_dedup`) is wrapped in a current-row `ROW_NUMBER() = 1` derived table, the same protection the FK-inferred path applies, so bridging to a history table doesn't fan the view out (the FROM anchor `joins[0]` is never wrapped). The CTE wrap layers on top of either:

```sql
CREATE VIEW ... AS
WITH base AS (
  SELECT <cols> FROM <from + joins + lookup_joins> [WHERE <filter>]
)
[, deduped AS (... ROW_NUMBER OVER (PARTITION BY <keys> ORDER BY <order_by>) = 1 ...)]
[, grouped AS (
  SELECT <gk_cols>, <agg_fn>(<col>) AS <col>, ... FROM <base|deduped> GROUP BY <gk_cols>
)]
SELECT * FROM <base|deduped|grouped>;
```

Phase 1 lookup joins (latest / aggregate / exists) sit inside `base` and compose with all CTE layers. Source-aligned products with no `:DatasetTransform` collapse to today's flat `SELECT ... FROM table` — no regression. Dedupe and grouping keys reference **product column names** (lowered through `_safe_name`); referring to source-only columns requires declaring them as suppressed product columns first (Phase 5 surface).

**Under-specified aggregation**: a grouped dataset whose non-grouping product column has no `aggregateFunction` falls back to `MAX(<col>) AS <col>` so the view still parses. The column name is surfaced in the renderer's `summary['underspecified_aggregates']` list so the engineer is prompted to set an explicit function in the TransformEditor.

**Explicit joins[] always wins** (Phase 4 design choice): when set, the engineer-declared list is authoritative. Any source table a mapping references but `joins[]` does not cover raises `ViewGenerationError` — refuse to silently emit a CROSS JOIN.

**Phase 4 joins[] authoring surface.** Engineer-facing: `routers/dataset_transform.py` exposes `GET /api/projects/{id}/dataset-transform?output_dataset_uri=...` and `PUT /api/projects/{id}/dataset-transform/joins`. The PUT validates each entry's shape (`alias`, `dataset_uri`, `kind ∈ {left,inner,right,full,cross}`, `predicate`), rejects malformed payloads with a 400 + per-index error list, and upserts both schema-side `:DataContractSchema-[:HAS_DATASET_TRANSFORM]->:DatasetTransform` (source of truth) AND ods-side `:DProdOutputDataset-[:HAS_DATASET_TRANSFORM]->:DatasetTransform` (the parallel copy view-DDL reads). Frontend mounts `JoinsOverridePanel.tsx` below the ServingWarningsCallout in the engineer's ProjectDashboard serving-card detail — one collapsible panel per output dataset. Per-row form is the default surface (alias text + kind dropdown + dataset_uri text + predicate textarea, with predicate disabled when kind=cross). A "View as JSON" toggle round-trips through `JSON.stringify/parse` for engineers who want to bulk paste or copy out; switching back to form mode revalidates the shape and blocks on syntax errors. Save mode-aware: JSON mode persists what's in the textarea directly so a textarea-only edit doesn't require switching back to form mode first. Known limitation: if the PO re-saves through the wizard, `_save_odcs_to_graph` wipes+recreates the schema-side `:DatasetTransform` from the YAML spec, which will clobber the engineer's joins[] override. Acceptable for v1 — the override is a transient "FK auto-discovery picked wrong, override this run" workflow, not a long-term schema decision.

**SCD-1 lowering** (Phase 5, `scd_policy.type='latest_only'`): when the PO declares latest-row-per-key semantics in the Shape step but has not authored explicit `dedupe`, view-DDL synthesizes a dedupe block: `keys` = product columns flagged `isPrimaryKey`, `order_by` = product column matching `_TEMPORAL_PATTERNS` (same matcher used for temporal-bridge detection), `direction='desc'`. The synthesized dedupe rides the existing `deduped` CTE machinery — latest_only and engineer-authored dedupe share one render path. Skipped silently when explicit dedupe already exists (engineer wins); surfaces `summary['scd_warning']` + a `-- warning:` comment when latest_only is declared but cannot be lowered (no primary key on the product, or no temporal column in product columns). `summary['scd_synthesized_dedupe']` records whether the lowering fired; `summary['scd_policy_type']` carries the raw declared type for surfaces. Other types (`snapshot`, `scd2`) parse onto `dt['scd_policy']` but are otherwise no-ops today.

**SCD-2 lowering** (Phase 5, `scd_policy.type='scd2'`): unlike SCD-1, SCD-2 does NOT synthesize anything — it's a contract-level declaration that "this view preserves history; here are the columns that carry the validity period". View-DDL's job is to (a) validate the named columns exist on the product, (b) warn if `dedupe` is also declared (semantic conflict — dedupe discards the history SCD-2 is supposed to preserve; engineer override still wins so dedupe runs and the conflict is logged), and (c) optionally append a derived `is_current` boolean column when `add_is_current=true`. The `is_current` expression is `(CASE WHEN <expiration_column> IS NULL OR <expiration_column> > CURRENT_TIMESTAMP THEN true ELSE false END) AS is_current` — portable across PG / Snowflake / Databricks / BigQuery. **Authoring**: wizard's Step 4 (Shape the Schema) renders an inline `Scd2PolicyPanel` (revealed when `shapeScdPolicy='scd2'`) — two dropdowns of product columns for `effective_column` / `expiration_column` + a checkbox for `add_is_current` (disabled until an expiration column is picked). Edit-mode hydration restores these from `spec.schema[0].transform.scd_policy`. Chat assistant `shape_set` accepts `scd_policy` as either a bare string (just the type) OR an object `{type, effective_column, expiration_column, add_is_current}` for SCD-2 — names get filtered against current schema state with per-field "ignored: not in schema" notes in the Apply chip. Summary surfaces: `summary['scd_effective_column']`, `summary['scd_expiration_column']`, `summary['scd_is_current_derived']` + a `-- scd-2:` audit comment naming both validated columns. `summary['scd_warning']` carries any validation failures (declared column not on product) or the dedupe-conflict note. ServingWarningsCallout renders a dedicated "SCD-2 history preserved" info signal showing both columns + the is_current state.

**Snapshot SCD lowering** (Phase 5, `scd_policy.type='snapshot'`): pins the view to one point-in-time slice. Required sub-fields: `snapshot_column` (a product column name) + `as_of_date` (string literal — engineer's responsibility to match the source's date format). View-DDL synthesizes a WHERE predicate `<alias>.<source_col> = '<as_of_date>'` on the base CTE, where alias + source_col come from the mapping that produced the named product column (so the filter goes against the actual source table, since WHERE evaluates before SELECT aliases in standard SQL). The synthesized predicate composes with any engineer-declared `filter` via `AND` so both narrowings apply. Defensive validation: missing `snapshot_column`, missing `as_of_date`, unknown product-column name, or a literal-kind product column (no source mapping to anchor) all surface in `summary['scd_warning']` and the filter is NOT applied. Successful lowering populates `summary['scd_snapshot_column']` / `summary['scd_snapshot_as_of']` / `summary['scd_synthesized_filter']=true` plus a `-- scd-snapshot:` audit comment at the top of the view. ServingWarningsCallout renders a dedicated "Snapshot SCD" info signal naming both column and date. **Authoring**: Cypher-only for v1; the wizard's Shape step only collects the `type` enum, so a PO declaring `snapshot` today still needs ops/engineer help to set `snapshot_column` + `as_of_date` (mirroring the v1 SCD-2 path before its wizard sub-panel shipped — Scd2PolicyPanel-equivalent for snapshot is a follow-up).

**suppressedColumns activation** (Phase 5, `:DatasetTransform.suppressedColumnsJson`): JSON list of product-column names removed from the final SELECT. The columns stay in the contract / `:DProdColumn` graph / `:ColumnMapping` graph (lineage, documentation, mapping authoring all intact) — the materialized view just doesn't project them. Primary use case is PII / sensitive data the consumer shouldn't see in the served view but the contract should still acknowledge. **Authoring**: per-column "Suppress" checkbox in the wizard's Shape the Schema step (collects into `suppressedColumns: Set<string>`, emits to `schema[0].transform.suppressed_columns`, round-trips through ODCS via `_canonicalize_dataset_transform`); PK columns disable the checkbox (the renderer would refuse anyway). Edit-mode hydrates from the existing spec so the checkboxes pre-tick on re-open. Cypher-only authoring also works for ops / migration scripts. Defensive cleanup at render time: PKs flagged `isPrimaryKey` are NEVER suppressed even if declared (would break the contract's stated key and SCD-1 dedupe synthesis) — surfaced as `summary['suppressed_pks_skipped']` + a `-- warning:` comment. Suppressed names that reference `dedupe.keys` / `grouping_keys` are silently filtered out of those lists (the SQL would otherwise reference a non-emitted column). Unknown declared names (typos) land in `summary['suppressed_unknown']`. Successful suppressions go in `summary['suppressed_columns']` + a `-- suppressed:` audit comment + the ServingWarningsCallout's info chip.

**Phase 6 window functions** (`:DatasetTransform.windowSpecsJson` + `transformKind='window'`). Named window declarations live on the dataset-level transform as a dict: `{<name>: {partition_by: [col, ...], order_by: [{column, direction}, ...], frame: "<raw SQL frame>"}}`. Column-level mappings reference a window by name via `transformParams.window` plus a `function` (LAG / LEAD / ROW_NUMBER / RANK / DENSE_RANK / NTILE / PERCENT_RANK / CUME_DIST / SUM / AVG / MIN / MAX / COUNT / COUNT_DISTINCT / FIRST_VALUE / LAST_VALUE / NTH_VALUE), an optional `offset` + `default` (for LAG/LEAD), or `ntile` (for NTILE). View-DDL's `_compile_window` emits `<FN>(<arg>) OVER (PARTITION BY ... ORDER BY ... <frame>)`. The function argument comes from the mapping's `transformInputs[0]` / `MAPS_SOURCE_COLUMN`; ranking functions (ROW_NUMBER / RANK / etc.) accept no argument. COUNT_DISTINCT lowers to `COUNT(DISTINCT ...)` for SQL portability. Defensive: a mapping referencing an undeclared window falls through to degenerate `OVER ()` (SQL still parses) and the name lands in `summary['window_specs_undefined']` + a `-- warning:` audit comment. Used windows land in `summary['window_specs_used']` + a `-- window: <name> = ...` audit comment per referenced spec. **Authoring**: PO declares windows in the wizard's Step 4 (Shape the Schema) via the collapsible `WindowSpecsEditor` panel — each row carries name, comma-separated `partition_by`, comma-separated `order_by` (parsed `"col [direction]"`), and a free-text frame clause. Stored client-side as an array of drafts for UI ordering, flattened to the `{name: spec}` dict at save time. Edit-mode hydration reconstructs the comma-text from the persisted dict. Chat assistant `shape_set` accepting `window_specs` is a follow-up. The mapping skill's `VALID_TRANSFORM_KINDS` accepts `'window'` so writers can persist it. **Engineer authoring**: `TransformEditor.tsx` has a `case 'window'` arm with a function dropdown (LAG / LEAD / ROW_NUMBER / RANK / DENSE_RANK / NTILE / PERCENT_RANK / CUME_DIST / FIRST_VALUE / LAST_VALUE / SUM / AVG / MIN / MAX / COUNT / COUNT_DISTINCT), a window-name text input, conditional offset+default fields for LAG/LEAD, and a buckets field for NTILE. The window-name is free-text rather than a dropdown (the editor doesn't currently fetch the contract's declared windows — typeahead is a follow-up); engineer types the name, view-DDL resolves at materialization, and unknown names surface in `summary['window_specs_undefined']` + the ServingWarningsCallout. Live SQL preview mirrors `_compile_window`'s argument shape so what the engineer sees in TransformEditor is what view-DDL emits.

**Phase 7 serving stage dialect picker.** `serving_virtual_view` stage has a single `config_fields` entry: `{key: 'dialect', label: 'Target SQL dialect', type: 'select', options_key: 'dialect'}`. `stages.py:get_config_options` returns the dropdown list (PostgreSQL / Snowflake / Databricks / BigQuery / ANSI SQL) plus `defaults.dialect='postgres'` so the picker pre-fills on a fresh stage. The prompt template references `{dialect}` and invokes `generate_view_ddl.py --dialect {dialect}`; `pipeline.py:build_prompt` pre-seeds `params['dialect']='postgres'` so pre-Phase-7 workflows that never set the field still format cleanly. The skill writes the dialect name into its sidecar summary, `store_serving_definition.py` reads it and persists `:ServingDefinition.targetPlatform` accordingly — `--platform` from the CLI is overridden by the sidecar so the stored DDL flavor always matches reality.

**Phase 7 dialect abstraction.** `generate_view_ddl.py` defines a `Dialect` class hierarchy — base `Dialect` (ANSI-portable fallbacks), `PostgresDialect` (default, matches pre-Phase-7 DDL), `SnowflakeDialect`, `DatabricksDialect`, `BigQueryDialect` — plus a `_DIALECTS` lookup keyed by name. Three SQL-emission paths divert through the dialect today: type-cast syntax (`pg`: `value::type`; others: `CAST(value AS type)`); SHA-1 / SHA-2 hashing (`pg`: `encode(digest(text, 'sha256'), 'hex')` via pgcrypto; `snowflake`: `SHA2(text, 256)`; `databricks`: `sha2(text, 256)`; `bigquery`: `TO_HEX(SHA256(text))`); `REGEXP_REPLACE` flags (`pg` needs explicit `'g'`; others are global by default). MD5 is universal but `bigquery` wraps it in `TO_HEX(MD5(...))`. CLI: `generate_view_ddl.py --dialect {postgres,snowflake,databricks,bigquery,ansi}` (default `postgres` for back-compat). `_DIALECTS` also registers a `"postgresql"` alias (→ `PostgresDialect`, for back-compat with `--platform`) and an `"ansi"` entry (the base `Dialect`); the lookup lowercases the name and falls back to `postgres` for anything unrecognised. The dialect name flows through the sidecar summary JSON; `store_serving_definition.py` reads it and overrides `--platform` with it, so `:ServingDefinition.targetPlatform` always matches the actual DDL flavor. Adding a new dialect: subclass `Dialect`, override only what differs, register in `_DIALECTS`. Most of the rendered SQL (SUBSTRING ... FROM ... FOR ..., ROW_NUMBER OVER, LEFT JOIN, GROUP BY, REPEAT, LENGTH, GREATEST, `||`) is already portable; the dialect only abstracts where targets genuinely diverge.

**Serving summary persistence + UI surface.** `generate_view_ddl.py` writes its structured per-view summary to `<output>.summary.json` alongside the DDL. `store_serving_definition.py` auto-loads the sidecar and persists it as `:ServingDefinition.summaryJson`. Backend (`summary.py:SERVING_QUERY{,_S}`, `marketplace.py` PRODUCT_DETAIL) returns the field on the serving rows. Frontend renders it via `components/ServingWarningsCallout.tsx`, mounted on the engineer dashboard's serving detail (above the table) and the marketplace product detail's Serving tab (per-view, default-open). The callout groups warnings by view and surfaces: `multiplication_warnings` (history-shaped sources without explicit dedupe), `auto_bridge_choice` (which junction tables the FK BFS picked and whether they were temporal-wrapped), `scd_warning` / `scd_synthesized_dedupe` (Phase 5 SCD-1 lowering state), `underspecified_aggregates` (grouped output columns that fell back to `MAX()`), and `suppressed_columns` / `suppressed_pks_skipped` / `suppressed_unknown` (Phase 5 suppressedColumns lowering state). Hidden entirely when every view's signal lists are empty so clean source-aligned products show no clutter.
