A walk-through for product owners, engineers, and the people who decide what to build.

Welcome. This deck walks through what the Data Workbench is, why it exists, and how it actually works in day-to-day use. Five sections plus a short appendix. About 25-30 minutes if presented end-to-end.
01
The paradigm
What problem are we solving, and how do data products fit?

The problem

  • Data products require many roles — Product Owners declare intent, Engineers build the pipeline, Stewards govern semantics, Quality Analysts validate.
  • Each step generates artifacts: schemas, profiling reports, quality rules, lineage, contracts, served views.
  • Without orchestration, those artifacts drift away from the contract they should fulfill.
  • Hand-coded glue between roles slows delivery and leaves accountability gaps.
  • The "right" data product is the one where the contract, the underlying data, the quality rules, and the served view all match.

The Workbench's job is to keep the contract, the graph, and the produced SQL in sync as the pipeline runs.

We're solving the coordination problem, not just the SQL problem. Each role produces artifacts that need to stay coherent with a single declared contract. The Workbench is opinionated about that coherence.

The solution

A web orchestrator built around contract-first data products and a knowledge-graph backbone:

One product = one contract
ODCS (Open Data Contract Standard) v3.1 declares what's promised. Authored in the wizard, or synthesised from approved graph state.
Graph-native
DCAT-2 datasets, DQV measurements, SHACL rules, PROV-O provenance, ODCS contracts, DPROD products — all in Neo4j.
Pipelines as workflows
Each archetype scaffolds an opinionated default; engineers add or remove workflow groups from a catalog.
Skill-driven stages
Each step is a Claude-driven skill with explicit inputs, outputs, and review surfaces. Same stages whether run from UI or CLI.
Four pillars. The contract is the source of truth, the graph is the persistence layer, workflows compose into pipelines, and skills are the unit of work. Skills are reusable Claude Code agents living in ~/.claude/skills/.

Architecture at a glance

Two React shells over one FastAPI backend. The backend dispatches stages through the Claude Code SDK, which invokes skills from ~/.claude/skills/. Skills do the actual work and write to Neo4j or PostgreSQL. SQLite holds pipeline state — stage status, run history, chat messages. CORS allows localhost:5173 (frontend) and localhost:3000.

Standards on top of the graph

Every artifact lives in Neo4j as typed graph nodes — no proprietary schema, no lock-in.

DCAT-2
W3C Data Catalog Vocabulary. :Catalog · :Dataset · :Column. Models the source database structure.
DQV
W3C Data Quality Vocabulary. Per-column measurements: nulls, distinct counts, percentiles, top values.
SHACL-inspired
Validation rules as :PropertyShape nodes anchored to :Column or :DProdColumn.
PROV-O
W3C Provenance Ontology. Audit trail for every review decision — who, when, with what evidence.
ODCS v3.1
Open Data Contract Standard. The :DataContract node. Authored in the wizard or synthesised from approved graph state.
DPROD
Data Product representation. :DProdDataProduct → :DProdOutputDataset → :DProdColumn chain.

Project-scoped URIs (catalog:{project_code}:...) keep two projects from colliding on shared tables. :CONSUMES is the only cross-project edge — it links a consumer contract to a source product.

Why standards matter: a future operator could query the graph directly with any DCAT-aware tool. Nothing here is Workbench-specific. The project-scoped URIs and the :CONSUMES contract are the only two opinionated choices.

How it works
Archetypes, workflows, walkthroughs, and the review gates.

Project archetypes

A project is a container of named workflow groups. The archetype picks the defaults.

ArchetypePersona-initiatedWhat it scaffolds
dd Data Discovery Engineer Discover, profile, enrich, score quality, apply domain rules, remediate. Standalone — no product output.
dq Data Quality Engineer Quality-only sub-flow on an already-discovered source. DQ rules, testing, scoring.
dpe-sa Source-aligned PO (3-step wizard) Discovery-first product. Engineer profiles the source DB; PO validates names + descriptions + observation rules + table classifications; engineer materialises ODCS from approved graph state.
dpe-cf Consumer-aligned PO (8-step wizard) Contract-first product. PO declares ODCS schema + which source products to :CONSUMES; engineer maps source columns into the contract; serves as a virtual view.

Coming soon: Data Modernization (dmod) · Data Migration (dmig).

Four implemented archetypes. The key split is dpe-sa vs dpe-cf — source-aligned products are discovery-first (the source DB is the starting point); consumer-aligned products are contract-first (the PO writes the schema before any source is touched). Engineer-only archetypes (dd, dq) are for analysis without producing a contract.

Workflows compose into a pipeline

The pipeline is workflow groups, each containing stages. Solid arrows mean "next stage runs"; dashed means "review gate". Reviews block downstream stages until cleared. This is the default scaffolding for a dpe-sa project — engineer can add Quality Assessment / Quality Testing / Remediation via "+ Add Workflow" if needed.

Source-aligned walkthrough dpe-sa

Source-aligned is the discovery-first flow. PO sends a lightweight idea ("mirror of employee master") with a name and domain. Engineer does discovery and enrichment. PO then opens a combined validation panel with four tabs — Names, Descriptions, Tables, Rules — and approves each. Engineer then runs the materialization stages, which synthesize the ODCS contract from approved graph state and emit a virtual view.

Consumer-aligned walkthrough dpe-cf

Consumer-aligned is contract-first. PO writes the wizard: declares the schema, picks which already-published source products to :CONSUMES, optionally authors Shape (dataset-level grain / filter / SCD / grouping). Engineer's job is purely mapping — link source columns from the consumed products into the consumer's contract columns. Serving stage emits a CREATE VIEW that joins across the source products' served views.

Reviews & approval gates

Every review surface is role-scoped and ties back to PROV-O provenance.

SurfaceOwned by
DescriptionsSteward (DQ/DD) · PO (dpe-sa)
MappingsReviewer
Unmapped columnsEngineer
Transformation escalationsSteward

Three actions on every queue:

Approve
Quality rating (acceptable / good / excellent). Auto-completes the stage when the queue empties.
Reject
Structured category + free-text. Re-runs go straight to the next stage; the rejection survives as :ProvRejectionReason.
Escalate (mappings only)
Flips mapping status to steward_review. Steward answers inline or adds to the catalog.
Reviews are first-class. Approve/reject decisions become PROV-O activities in the graph — full audit trail of who reviewed what, when, with what quality rating, and any rejection reason. The Workbench auto-flips stage status to "complete" when its review queue empties, so engineers don't have to manually close stages.

DQ rules: four sources

A single rule lifecycle ('pending_review' → 'approved' / 'rejected'); the ruleSource tells you where it came from.

observation
Auto-discovered by data-quality-rule-generation from profiling stats. Anchored to :Column.
e.g. "this column is 99.4% non-null → propose mandatory rule"
domain
Generated from playbook/domain_catalogs/{domain}.yaml reference files. Anchored to :DProdColumn.
e.g. HR domain says "employee_id must be 7-digit numeric"
user
PO-authored via wizard chat assistant (applies_to: rule_create). Auto-approved.
e.g. "tenure_years must be >= 0"
spec
Embedded in ingested ODCS quality[] blocks. Materialised by _materialise_spec_rules. Status approved.
e.g. inherited from another team's published contract

The Workbench summary card filters by source so reviewers see exactly the bucket they own.

The four-source taxonomy is one of the more load-bearing design choices. observation rules are evidence-based; domain rules are policy-based; user rules are PO declarations; spec rules ride along with an ingested contract. Reviewers see them all in one detail view but can filter to their own bucket.

DQ scoring: 8 dimensions

Scoring reads existing graph evidence — no new SQL gets run. The score is a function of what's been measured (DQV) plus what's been declared (PropertyShape rules). Documentation and Grounding extend the classic 6 dimensions with governance maturity signals. Re-scoring after remediation lets teams track quality improvement over time.

03
Data transformations
Column-level kinds, dataset-level Shape, SCDs, and multi-dialect SQL.

Two layers of transformation

Column-level

One :ColumnMapping per (source columns → product column). Structured DSL, not free-text SQL.

Each mapping carries:

  • transformKind — one of 15 kinds
  • transformInputs[] — source columns
  • transformParams — kind-specific config
  • transformDecorators — trim / upper / lower / etc.
  • transformAuthor — provenance bucket

Dataset-level Shape

One :DatasetTransform per output dataset. Layers as SQL CTEs above the SELECT.

Each shape carries:

  • filter — raw WHERE fragment
  • dedupe — ROW_NUMBER over keys
  • grouping_keys — GROUP BY columns
  • joins[] — explicit FROM/JOIN graph
  • scd_policy · suppressed_columns · window_specs

Four-source transformAuthor mirrors the DQ rules pattern: po_hint → steward_catalog → engineer → ai_suggestion — fallback order when seeding the mapping queue.

Column-level says "how does THIS column get computed". Dataset-level says "what's the shape of the whole output table". They compose: column transforms compile into SELECT expressions; dataset Shape wraps them in CTEs (filter, dedupe, grouping, joins, SCD).

The structured DSL means the engineer doesn't write SQL — they fill in a form, and view-DDL compiles it to dialect-specific SQL.

Deep dive — bucket · mask · hash

bucket
Continuous → ordered bands. {boundaries: [30, 50, 70], labels: ["young", "adult", "senior", "elder"]} compiles to a CASE WHEN chain. N+1 labels for N boundaries.
mask
Format-preserving redaction. {algorithm: "keep_last", keep_n: 4, mask_char: "X", keep_format: true} turns 4111-1111-1111-1234 into XXXX-XXXX-XXXX-1234.
hash
Irreversible digest. {algorithm: "sha256", salt: "..."}. md5 is built-in PG; sha1/sha256 use pgcrypto's digest(). Not a security primitive — salt is for namespace separation, not protection.
-- bucket(age)
CASE WHEN age < 30 THEN 'young'
     WHEN age < 50 THEN 'adult'
     WHEN age < 70 THEN 'senior'
     ELSE 'elder' END AS age_band

-- mask(card_number, keep_last, keep_n=4)
REGEXP_REPLACE(
  SUBSTRING(card_number FROM 1
    FOR LENGTH(card_number) - 4),
  '[A-Za-z0-9]', 'X', 'g'
) || RIGHT(card_number, 4)
  AS card_masked

-- hash(ssn, sha256)
encode(
  digest(ssn || 'salt', 'sha256'),
  'hex'
) AS ssn_hash
bucket = discretization. mask = format-preserving redaction. hash = irreversible digest. All three are very common privacy / governance asks. Generated SQL shown for PostgreSQL; Snowflake / BigQuery emit slightly different syntax for the hash one — that's covered in the dialects slide.

Deep dive — lookup selection strategies

equi — default
LEFT JOIN ref ON src.fk = lk.key
Returns lk.value_column.
Classic dimension lookup.
latest
Derived-table join with ROW_NUMBER() OVER (PARTITION BY key ORDER BY {order_by_column} DESC) = 1.
For current_X / most_recent_X patterns.
aggregate
Derived-table join with GROUP BY key. Function ∈ SUM · COUNT · AVG · MIN · MAX · COUNT_DISTINCT.
For total_orders / avg_score patterns.
exists
Same equi shape, but SELECT becomes (lk.key IS NOT NULL).
For has_X / is_X boolean flags.

Dedup: two product columns sharing the same history-table scan emit one derived-table join, not two — view-DDL dedups by (table, key, strategy, order_by, filter_clause).

Lookup is the heaviest-used kind. Four strategies cover the common patterns: classic equi-join, latest-row-per-key, aggregated-per-key, and existence-flag. The derived-table dedup is important — without it, a product with 10 history-table fields would emit 10 redundant scans.

Deep dive — window functions

Windows are declared at the dataset level in :DatasetTransform.window_specs and referenced by name from column mappings.

Why separate? Reuse — one named window is often referenced by several columns.

Supported functions
LAG · LEAD · ROW_NUMBER · RANK · DENSE_RANK · NTILE · PERCENT_RANK · CUME_DIST · SUM · AVG · MIN · MAX · COUNT · COUNT_DISTINCT · FIRST_VALUE · LAST_VALUE · NTH_VALUE
// dataset-level
"window_specs": {
  "by_employee_date": {
    "partition_by": ["employee_id"],
    "order_by": [
      {"column": "hire_date", "direction": "asc"}
    ],
    "frame": "ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW"
  }
}

// column-level mapping
{
  "transformKind": "window",
  "transformInputs": ["salary"],
  "transformParams": {
    "window": "by_employee_date",
    "function": "LAG",
    "offset": 1,
    "default": null
  }
}

Compiles to: LAG(salary, 1, NULL) OVER (PARTITION BY employee_id ORDER BY hire_date ASC ROWS BETWEEN ...) AS prev_salary

Windows let the Workbench emit any of the standard PARTITION BY / ORDER BY analytics patterns. Named so they can be shared — three columns "previous salary", "salary rank", "running total" can all share one by_employee_date window. Unknown window names fall through to OVER () and surface as warnings in the serving summary.

Dataset-level Shape

Schema-level peer of column-level transforms. One :DatasetTransform per output dataset. Each field layers as a CTE.

filter
Raw WHERE fragment applied as the first CTE.
dedupe
ROW_NUMBER OVER keys, latest per natural key.
grouping_keys
GROUP BY keys; activates per-column aggregateFunction.
joins[]
Explicit FROM/JOIN — bypasses FK auto-discovery.
scd_policy
latest_only · scd2 · snapshot (next slide).
suppressed_columns
Drop from view; stays in contract / lineage. PK refusal.
window_specs
Named windows referenced by window-kind mappings.
grain_prose
"One row per X" documentation; no SQL effect.

PO authors these in the wizard's Shape and Shape the Schema steps; engineer can override per-output-dataset via the Joins override panel on the project dashboard.

Eight fields, all optional. When none are set, view-DDL emits a flat SELECT (source-aligned products that mirror the source 1:1 usually need nothing here). The fields layer in a fixed order: filter → dedupe → grouping → final SELECT, so the CTE chain is predictable.

Slowly-Changing Dimensions

Three SCD types covered today. latest_only synthesises a dedupe and is the most common. scd2 keeps history and is the right choice for slowly-changing dimensions where downstream wants the change record. snapshot pins the view to one as_of_date — useful for regulatory reporting where you need to reproduce yesterday's view.

Multi-dialect SQL emission

One Dialect abstraction; five target platforms.

DialectCastSHA-256REGEXP_REPLACE flag
postgresvalue::typeencode(digest(t,'sha256'),'hex') (pgcrypto)explicit 'g'
snowflakeCAST(value AS type)SHA2(t, 256)global by default
databricksCAST(value AS type)sha2(t, 256)global by default

Picked via the serving stage's "Target SQL dialect" dropdown. The chosen dialect rides through to :ServingDefinition.targetPlatform so the persisted DDL knows its flavor.

Most rendered SQL (SUBSTRING ... FROM ... FOR · ROW_NUMBER OVER · LEFT JOIN · ||) is already portable; the Dialect class only abstracts where targets diverge.

Multi-dialect emission means a consumer running on Snowflake doesn't get pgcrypto-flavored DDL. Adding a new dialect: subclass Dialect, override only what differs, register in _DIALECTS. The vast majority of view-DDL is already cross-platform — only cast, SHA hashing, and regex flags diverge in practice.

Capabilities you'll use daily
Chat assistants, Apply protocol, active learning, CLI execution.

Two chat assistants, one graph

Guide me (PO)

In every wizard step. Coaches the PO through authoring.

  • Suggests idea / domain / name / dataset name
  • Drafts descriptions and purpose statements
  • Proposes columns from the domain catalog
  • Authors quality rules (auto-approved)
  • Sets column-level transform hints
  • Authors dataset-level Shape (filter / SCD / grouping)
  • Sibling sub-skill data-product-name-advisor

Ask (Engineer)

Right-side drawer on every project page. Read-only.

  • Ad-hoc Cypher queries against project's Neo4j
  • Quality-score interpretation
  • Lineage walking (where does X come from?)
  • Failure diagnosis (what went wrong in stage Y?)
  • Workbench-concept explanations in-context
  • Every fact backed by a visible Cypher query
  • Suggestion chips adapt to the current screen

Both chats run on Claude Code SDK with constrained tools. Engineer Ask is hard-scoped to its project via --project-code at every Cypher call.

Two different sub-skills, two different system prompts, two different sets of allowed tools. The PO chat can write suggestions but doesn't directly mutate state (the wizard's Apply protocol does that). The engineer chat is read-only end-to-end — its job is explanation, not mutation.

Apply protocol

PO chat emits structured suggestion blocks; the wizard auto-applies them into form fields.

Partial-update semantics across all Apply types: absent fields preserve current state. The PO can iterate ("now also add a department_id") without losing earlier authoring.

Apply turns natural-language coaching into form mutations. Critically the chat doesn't directly write the contract; it emits a suggestion the wizard applies. The PO sees the Apply card render in chat with a button, can click to accept or ignore. This keeps human authorship in the driver's seat.

Active learning

The playbook-reflector skill analyses approve/reject decisions plus high-quality examples and proposes generic domain-playbook rule updates. A :PlaybookVersion tracks every cycle so engineers can roll back. Next time the relevant stage runs, a baseline-vs-refined picker lets the engineer choose which playbook to use.

Active learning closes the loop. Reviewers reject descriptions or mappings with reasons; reflect-on-reviews analyses the patterns and proposes generic rule updates to the domain playbook. Versioned, so a bad reflection cycle is rollback-able. The Learning History dashboard card surfaces how many cycles have run for a project.

Advanced topics for follow-up reading.

Appendix · Auto-bridge & FK inference

When the engineer maps columns from two tables that aren't directly FK-connected, view-DDL discovers a join path through unmapped intermediates.

  • BFS over the FK graph — shortest path between mapped tables. Unmapped intermediates are auto-included in FROM/JOIN scope (no SELECT contribution).
  • Name-similarity ranking when multiple shortest paths exist: a junction whose name contains both endpoint names (department_employee) outranks one that contains only one (department_manager).
  • Relationship-kind tie-break: general_membership ≫ fact / lookup_dimension ≫ specialization. Classification set during metadata enrichment, approved by PO in Tables tab, propagated to :DProdOutputDataset.relationshipKind.
  • Temporal-bridge wrapping: if the bridge has to_date / valid_to / *_at columns, auto-wrap with ROW_NUMBER() OVER (...) = 1 so the bridge contributes the latest row per natural key.
  • Multiplication warnings for non-bridge temporal sources — engineer must author explicit :DatasetTransform.dedupe.

Override at any time: declare explicit joins[] in the dataset Shape, or use the engineer's Joins override panel.

Appendix · PROV-O audit trail

Every review decision becomes a graph node — full audit trail.

  • :ProvActivity — the act of reviewing (with activityType: 'description_review' | 'mapping_review' | ...)
  • :ProvAgent — the user (role + email)
  • :ProvRejectionReason — structured category + free-text on reject
  • :ProvQuality — quality rating on approve (acceptable / good / excellent)
  • :ColumnDescription · :ColumnMapping · :PropertyShape — link to the activity that approved them

Surfaces in the UI: every detail row's Provenance column shows a View button that opens the audit trail — who generated it, who reviewed it, when, what was rejected before, and the final approval evidence.

Used in chat too: when the Engineer Ask agent makes a claim about data quality, the supporting Cypher walks through the PROV-O chain to back it up.

Appendix · Versioned contracts

Editing a published product branches a new :DataContract version so the public listing doesn't leak draft edits.

  • First save after Edit click triggers CREATE_NEW_VERSION: v2 starts at lifecycleState='draft', isCurrent=true; v1 stays at prior state with isCurrent=false.
  • Linked via :PROV_WAS_DERIVED_FROM.
  • Marketplace pinning: head(collect(dc) ORDER BY lifecycleVersion DESC) pins to the latest published / superseded version, falling back to isCurrent=true only if no version was ever deployed.
  • dprod-leak mitigation: :DProdColumn / :DProdOutputDataset are NOT versioned. _generate_dprod wipes and rebuilds them from whatever is isCurrent=true. Wizard skips /generate-dprod when hydrated state is published so column data doesn't flip mid-edit.
  • Engineer banner: shows when an edit-kind ProductRequest is pending; client-side diff computed via lib/editDiffImpact.ts for impact preview.
