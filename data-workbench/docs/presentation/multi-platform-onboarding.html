Data Workbench architecture proposal

Multi-Platform
by Design

A repeatable onboarding architecture for discovering from and deploying to PostgreSQL, MySQL, Snowflake, Databricks, and the platforms that follow.

Architecture committee briefing 30 slides 16 July 2026
Frame this as a platform design, not four database integrations. The goal is to establish one controlled onboarding path that keeps PostgreSQL behavior stable while allowing database-specific behavior to evolve independently.

Executive thesis

Keep practitioner workflows stable. Move platform variability behind explicit, testable adapter contracts.

Capability-oriented skills

Discovery, profiling, compilation, deployment, and verification remain the user-facing units.

Typed semantic core

A platform-neutral IR carries transformation intent; the selected target determines SQL and DDL.

Isolated adapters

Each platform owns metadata, rendering, execution, lifecycle, and capability evidence.

This is the middle path between platform-skill sprawl and a fragile multi-platform “uber skill.”
Lead with the division of responsibilities. Skills express workflow and intent. The core owns contracts and planning. Adapters own deterministic database behavior. This lets practitioners use one workflow while engineers qualify each platform capability independently.

Hidden coupling

Prompt construction, stage dispatch, DSN parsing, error handling, DDL lifecycle, and smoke tests assume Postgres.

False confidence

Having a partial Snowflake or Databricks renderer is not platform support. Credentials, discovery, deployment, verification, and operations must also pass.

The key point is that a new driver cannot solve the problem. Platform assumptions exist in data contracts, UI routing, execution, deployment lifecycle, and testing. Existing dialect classes prove only that some expressions can be rendered.

Design principles

Guardrails that keep expansion from breaking the platform

Target determines dialect

Users select a target and serving intent. They do not independently choose SQL that can contradict the target.

Fail closed

Unknown platforms, unsupported capabilities, or lossy transforms return actionable errors. No silent Postgres fallback.

Execution boundary, not vendor label

A native view is legal only when one target identity can resolve every source relation at query time.

Secrets remain references

No reusable DSNs in graph data, prompts, logs, generated projects, or API reads.

One semantic source of truth

Preview, view DDL, dbt models, and verification derive from the same typed transformation IR.

Postgres compatibility is measured

Characterization tests, golden SQL, live regression, and a compatibility facade precede migration.

These principles address the known failure modes: target/dialect drift, false same-platform assumptions, secret leakage, preview/deploy divergence, silent semantic weakening, and accidental Postgres regression.

Skill design

Compare the three structural choices

Option A

Platform skill per capability

Strong isolation, but multiplies discovery, profiling, serving, remediation, and evaluation assets for every platform.

skill sprawl
Option B

One multi-platform skill

Fewer skills, but prompts, scripts, and tests become branch-heavy. Tuning one target can regress another.

fragile coupling
Recommended

Capability skill + adapter

One practitioner workflow delegates deterministic platform work through stable contracts and lazy-loaded references.

bounded change
The recommendation keeps progressive disclosure at the workflow level. Platform-specific instructions can live as adapter resources loaded only when selected, but platform execution code does not live in prose-heavy sibling skills.

Component boundaries

Put policy in the core and mechanism in adapters

  • Questions and explanations
  • Platform-neutral inputs/outputs
  • Progressive references

Core services

  • Contracts and canonical types
  • Capability and connection registries
  • Serving-plan policy
  • Run state and audit events

Platform adapter

  • Metadata discovery
  • SQL and DDL rendering
  • Execution and error taxonomy

A new platform should add a manifest, providers, fixtures, and a dossier—not new branches throughout the application.
This is the practical modularity rule. Core policy decides whether a route is allowed; adapters prove whether a platform can execute it. Skills remain readable and stable because they consume capability contracts rather than driver APIs.

Resolve at runtime

The execution boundary resolves credentials only for the provider and purpose authorized for that run.

One instance can have separate read, deployment, and administrative profiles. This prevents a discovery credential from becoming an accidental deployment credential and makes source-versus-target decisions explicit.

Adapter-owned

Catalog hierarchy, raw type parsing, quoting, statistics queries, error mapping.

Core-owned

Output schema, canonical types, stable IDs, provenance, capability maturity.

Fail visibly

Partial privileges and unsupported metadata are explicit findings, not empty successful results.

Discovery should never install packages at runtime. Adapters ship with pinned dependencies. Every discovery artifact records which adapter, profile, and capability evidence produced it so later planning can determine whether the metadata remains trustworthy.

Decision timing

Bind decisions only when the necessary evidence exists

Step 1

Register

Choose platform type and create instance/profile references. Validate connectivity and identity.

Step 2

Discover

Bind source relations to physical identities and record capability evidence.

Step 3

Model

Keep product intent and transformations platform-neutral in the typed IR.

Step 4

Plan serving

Select target profile and strategy from reachability, policy, semantics, freshness, and cost.

Step 5

Compile & run

Dialect follows the target. Deploy only after conformance and preflight checks.

Do not choose a target dialect during source discovery. The model remains portable until serving planning. At that point the target, execution boundary, and required semantics are known, so compilation can be deterministic.

This is the lowest-latency path and can preserve source freshness, but only if all inputs are visible and target view semantics match the product contract. MySQL DDL implicit commits, for example, change the compensation plan even though CREATE OR REPLACE VIEW exists.

Pattern B

When platforms differ, transport is a separate concern

Source platformMySQL / Postgres / other
Transfer providercheckpoint + schema evolution
Target stagingtarget-visible, reconciled data
dbt / native pipelinetarget-local transformation
Data productverified target artifact

Transfer proves

Offsets, retries, ordering expectations, schema changes, deletes, and source-to-stage reconciliation.

Transformation proves

Target SQL compilation, model ordering, tests, target grants, and product semantics.

Do not conflate

dbt transforms relations already visible to its target. It is not the heterogeneous transport layer.

This separation is operationally important. A failed transfer has different checkpoints and recovery semantics from a failed model build. It also lets a MySQL source feed a certified Snowflake or Databricks target even while MySQL dbt materialization remains unsupported.

SQLGlot’s role

Parse, inspect ASTs, validate target syntax, and perform bounded translation with unsupported operations raised as errors.

SQLGlot is not the proof

Best-effort translation cannot establish semantic equivalence. Schema-aware target compilation and live fixtures remain mandatory.

Source: SQLGlot repository and documentation (MIT).
The typed IR prevents the common mistake of using one platform’s SQL as the canonical representation. SQLGlot is valuable infrastructure but should run in fail-closed mode and be paired with schema information and target execution tests.

Certification requires semantic fixtures on a live target—not merely emitted SQL or parser acceptance.
This slide is the response to the iterative Postgres experience. The test corpus must target values that expose dialect differences: nulls, time zones, precision edges, Unicode, duplicate join keys, nondeterministic ordering, and DDL failure points.

Controlled execution

Deployment is an auditable run, not one SQL call

Immutable run inputs

IR version, source bindings, target profile, adapter versions, artifacts, policy decision.

Platform lifecycle

Transaction where available; otherwise staged apply, compensation, and explicit partial-failure state.

No ambiguous success

A created object that fails verification is not deployed. Record failure and execute the provider’s recovery plan.

Different databases have different DDL atomicity. The common state machine preserves a consistent user and API contract while each deployment provider implements the correct transaction or compensation mechanism.

Headless operation

The API uses the same plan contract as the UI

POST /v2/serving-plans { "product_version": "dpv_421", "source_bindings": ["src_mysql_orders"], "target_profile": "snowflake_prod_writer", "intent": { "freshness": "daily", "physical": true } } 202 Accepted { "plan_id": "plan_8031", "strategy": "transfer_then_dbt", "dialect": "snowflake", "capability_snapshot": "caps_119", "state": "planned" }

Idempotent

Client request keys and immutable plan versions prevent duplicate deployment.

Inspectable

Plan rationale, restrictions, artifacts, events, and evidence are retrievable.

Event-driven

Long-running discovery, transfer, dbt, and verification runs expose status and cancellation.

Headless clients should not recreate the serving decision logic. They provide target and intent, receive a deterministic plan, then execute that plan through idempotent run APIs. UI and automation therefore cannot diverge.

Technology governance

A strict permissive-license and community-health gate

Allowed licenses

Apache-2.0, MIT, BSD-2-Clause, BSD-3-Clause, PostgreSQL, and comparable permissive licenses.

allowlist

Not accepted

GPL, LGPL, AGPL, SSPL, BSL, ELv2, or other source-available/non-OSI dependency paths.

including transitive

Community evidence

Recent maintenance plus multiple contributors, releases or active commits, responsive issues, and meaningful downstream use.

reviewed annually
License approval is not platform certification. Each dependency must also pass security, compatibility, performance, and operational qualification.

Build gate

Generate SBOM, scan direct and transitive licenses, pin versions, verify provenance, and block policy violations.

Lifecycle gate

Record owner, supported version envelope, release cadence, end-of-life trigger, and replacement plan.

This is intentionally stricter than simply checking the top-level project license. Connector and adapter dependency trees matter. The policy should run in CI and be repeated at every dependency update.

Implementation sequence

Build the platform once; onboard capabilities incrementally

Phase 0

Characterize

Freeze Postgres behavior with golden artifacts, semantic fixtures, and live regression. Establish license/SBOM policy.

Phase 1

Foundation

Connection registry, secret refs, physical identity v2, canonical types, capability registry, provider SPI.

Phase 2

Discovery

Qualify metadata and read providers: MySQL first, then Snowflake and Databricks. Expose capability maturity.

Phase 3

Compile & serve

Typed IR, target renderers, native view lifecycle, approved Snowflake/Databricks dbt adapters.

Phase 4

Move & operate

Transfer provider, reconciliation, run telemetry, recovery drills, then optional federation evaluation.

Release capability-platform pairs independently; keep unsupported routes unavailable rather than weakening the contract.
MySQL is useful as the first discovery adapter because the repository already contains an orphaned experiment, but that code must be repackaged and tested. Snowflake and Databricks then exercise multi-catalog identity and approved dbt target paths.

Conclusion

One onboarding template, controlled variation

For practitioners

Stable workflows, visible support levels, explainable serving plans, and the same behavior in UI and headless automation.

For platform engineers

Narrow provider contracts, isolated dependencies, reusable conformance suites, and independent adapter versioning.

For architecture & risk

Explicit execution boundaries, fail-closed semantics, auditable runs, and a strict permissive-license supply chain.

For delivery

Incremental capability releases without pretending every platform supports every deployment route.

The durable unit of extension is a certified capability provider—not a vendor branch in every workflow.

Close on the unit of extension. This design makes future platforms routine: a dossier, manifest, providers, fixtures, and certification evidence. It does not require restructuring practitioner workflows or weakening existing Postgres guarantees.
