About this model

      
A logical data model for a property and casualty insurer, organized by subject area and aligned with ACORD naming and structure. Every entity carries a definition and its corresponding ACORD XML aggregate; every attribute carries its key role, logical and physical data type, optionality, business definition, ACORD element path, and code list.

      
Scope and attribution. This is an ACORD-aligned model, not a reproduction of the ACORD Reference Architecture, ACORD Data Model, or ACORD XML/AL3 standards, which are licensed by ACORD to its members. Entity and element names follow ACORD P&C XML conventions (e.g. PersPolicy, ClaimsOccurrence, LOBCd, NatureInterestCd) so the model maps cleanly to ACORD messages; element paths are indicative. Confirm paths and code values against the licensed specification before production use. ACORD is a registered trademark of ACORD Corporation.

Modeling conventions

      
    
        
  • Party pattern. People and organizations are stored once as Party and play roles through association entities (PolicyParty, ClaimParty, AdditionalInterest, Producer, Carrier).
    • 
        
  • Policy versus term. Policy holds facts that persist across renewals; PolicyTerm holds each contract period; PolicyTransaction records every change that versions a term.
    • 
        
  • Insurable object supertype. InsurableObject is the common parent of Building, Dwelling, Vehicle and ScheduledItem (shared primary key), so coverages, interests and claims attach uniformly.
    • 
        
  • Coverage structure. Coverage belongs to a PolicyLine and optionally an insurable object; Limit and Deductible are children, mirroring ACORD's Coverage/Limit and Coverage/Deductible.
    • 
        
  • Claim financials at feature level. Reserves, payments and recoveries attach to ClaimFeature (one claimant on one coverage), which supports Schedule P and statistical reporting.
    • 
        
  • Effective dating. Role and association entities carry EffectiveDt/ExpirationDt; transactional history is reconstructed from PolicyTransaction.
    • 
        
  • PII. TaxId, BirthDt, DriversLicenseNumber and payment instruments should be encrypted or tokenized and access-controlled.
